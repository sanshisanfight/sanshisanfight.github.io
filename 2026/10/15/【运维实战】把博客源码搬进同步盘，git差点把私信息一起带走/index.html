【运维实战】把博客源码搬进同步盘，git 差点把私信息一起带走

发表于2026-10-15|更新于2026-10-22|云原生运维
|总字数:3k|阅读时长:10分钟|浏览量:

今天干的事一句话说完：把个人博客的源码从老目录搬进百度同步盘，给它补上 git 版本控制，然后把所有隐私信息擦干净。

听着像体力活，实际卡了整整一下午。三个坑里有一个我到现在想起来还后背发凉——不是难，是我差点把真实邮箱和本地路径亲手推到 GitHub 上。

这篇写完整过程，包括我认为最值得记住的那条认知。

一、最隐蔽的坑：git add 了，但文件其实没进去

搬完源码我照常 git add . 提交。然后去翻目录，发现不对——提交记录只有一条，指针大小 160 字节。

我明明 add 了一个含 248 个文件的主题目录。

一 ls，.git 赫然躺在那里。

根因：gitlink

当一个子目录自带 .git 时，git 不会把它当普通文件夹，而是记成一条 gitlink——只存一个指向那个子仓库的指针（tree mode 160000），不存里面的文件。

后果是什么？

  • git status 永远干净，你以为提交完了
  • 换台电脑 clone，主题目录是空的
  • 博客直接构建失败，而且很难查，因为本地一切正常

解决

为什么没用 git submodule

submodule 是 git 官方正规方案，但我这个源码在百度同步盘里，同步盘环境访问 GitHub 并不稳定，submodule 的 clone/fetch 失败率高。而且 submodule 存的也只是 commit hash，换机时仍需额外拉子仓库。

所以我选了土办法：把主题源码物理纳入主仓库。248 个文件、4.7MB，一次 clone 到位。

判断方法：某目录 git add 后提交内容异常少（比如只有一条 160 字节记录），先看它里面有没有 .git。

二、最容易被忽略的坑：14137 个小文件是同步盘的性能杀手

搬源码时我纠结了很久：整个博客目录 135MB，搬不搬？

最后决定只搬 16.9MB / 433 个文件。

目录 体积 文件数 决策
source/ 10.7MB 17 搬
themes/ 6.3MB 396 搬
scaffolds/ + .github/ + 配置 ~300KB 9 搬
node_modules/ 85.1MB 14137 不搬
public/ 13.7MB 76 不搬
.deploy_git/ 26.1MB 701 不搬

为什么小文件特别致命

百度网盘这类同步盘需要持续扫描目录树做增量对比。14137 个文件意味着它一直在扫，磁盘 IO 和同步流量全被吃掉。

能重建的一律不搬。 这样既控制了同步盘负担，也保证了「源码仓库是唯一事实来源」。

搬完我还校验了源和目标的体积完全一致。这步别省——同步盘大文件传输中断是常事。

三、最痛心的坑：删了文件，历史里还在

这个坑是等我想 push 的时候才发现的。

我先做了常规脱敏——工作区里的真实邮箱、Windows 用户名、本地磁盘路径全部替换掉，占位符一套，行云流水。

但当我准备推到 GitHub 时突然反应过来：

git 存储的是每一个提交的历史快照。

我改的是最新那一个版本。前面 9 个提交里，真实邮箱和路径原封不动地躺着。仓库一旦公开，这些全都能被挖出来。

第 1 层：替换文件内容（tree-filter）

第 2 层：替换提交元信息（env-filter）

两层必须同时做。 tree-filter 只管文件内容，env-filter 只管提交元信息（作者、提交者、邮箱）。只做一层，另一层照样残留。

第 3 层：三个后置动作，漏一个都不彻底

refs/original/ 是 filter-branch 自己创建的备份引用。很多人只跑完 filter-branch 就以为完事了，结果这个引用还把脱敏前的历史完整保留着。

第 4 步：全量校验（不能只看最新提交）

401 个 blob 扫完无残留，作者邮箱唯一值是 noreply。这才算完。

顺便提一个细节

执行 filter-branch 时我被 SIGTERM 打断了。原因是 --tree-filter 需要逐个提交 checkout 全部 401 个文件，放在同步盘目录下 IO 极慢。

改写本身其实已经完成，手动补齐收尾步骤即可：

如果能重来，我会把仓库放在本地 SSD 完成历史重写，重写完再移回同步盘；或者直接用 git filter-repo（官方推荐，快一个数量级，但需要额外装 Python 包）。

四、顺手修的：Windows 中文 bat 脚本的编码坑

我还修了个 deploy.bat——双击一键部署 Hexo 博客的脚本。

双击之后输出错乱，出现 echoHexo 这种粘连命令，REM 注释行被当命令执行。

根因

CMD 解析 UTF-8 中文 bat 时错乱。默认代码页下中文是多字节，字符宽度导致命令与参数之间的空格分隔符丢失，echo 和参数被粘成 echoHexo。

解决：脚本正文全部改纯 ASCII

用 %~dp0 自动定位脚本所在目录，还有个附带好处：整个博客文件夹可以随意移动或改名，脚本不用改。

行尾也要统一，并在 .gitattributes 里声明：

这个 .gitattributes 解决的是另一件事：Windows 上 git 持续提示 LF will be replaced by CRLF。仓库无行尾契约时，git 按本地 core.autocrlf 行为转换，跨平台构建会出问题。.gitattributes 是仓库级契约，优先级高于本地配置。

五、另外两个小坑

5.1 脱敏文档自己的示例被误判为泄露

我在脱敏记录文档里写「原文是 C:\Users\<用户名>\，改为 python -c」，想说明替换前后对比。

结果跑自动扫描，把我文档里的示例值判成了隐私残留。

改法：示例值也统一写成 <用户名>、<BLOG_DIR> 这类纯占位符，一个真实字符都不留。

5.2 Git Bash 下批量替换反斜杠路径失败

sed -i 's|C:\\Users\\xxx|...|' 和内联 Python 替换都失败，反斜杠转义层层叠加，正则被彻底破坏。

可靠做法：写临时 .py 脚本文件执行，或用编辑工具逐处替换。 不要用内联转义处理 Windows 反斜杠路径。

六、脱敏规范清单

公开内容输出（博客 / 文档 / 开源项目）建议按下表处理：

类别 示例 处理方式
本地用户名与路径 C:\Users\<用户名>\ 改为通用命令，如 python -c "..."
个人磁盘路径 <个人磁盘>:\... 改为 <BLOG_DIR> 等占位符
真实邮箱 <真实邮箱> 改为 noreply 格式
内网 IP / 公司域名 192.168.x.x、内网域名 改为 192.168.100.101、example.com
密钥 / Token / 证书 任意 一律用 xxx 代替
客户名 / 工单号 任意 删除或改写
终端截图 — 注意裁剪顶部路径与登录用户

可保留：作者昵称、GitHub 用户名（若图片 CDN 依赖该用户名，改名会导致所有历史文章图片失效）、已公开的技术内容。

关于 noreply 邮箱：格式是 用户ID+用户名@users.noreply.github.com。即使仓库公开，GitHub 也不会把真实邮箱关联到账号。这是「公开代码但不暴露私人邮箱」的标准做法，建议所有公开仓库的 git 配置都换成它。

七、最终验证

全部通过后即可安全推送到公开远端。

今日收获

1. git 的每一个提交都是不可变的历史快照。你今天删除的信息，在昨天的快照里依然活着。

这个认知是我准备 push 的那一刻才真正建立的。之前我一直以为「改了文件、提交了，就等于删掉了」——完全错。给做公开内容输出的朋友一个建议：脱敏从第一次提交就开始做，别等要发布才回头擦。我今天是事后补救，近一半时间花在历史重写和校验上。

2. 「能重建的一律不搬」是迁移的第一原则。

node_modules、public、.deploy_git 都是可重建产物。14137 个小文件对同步盘是持续的性能消耗，而 npm install 一条命令就能拿回来。源码才是唯一需要搬运的资产。

3. 当 git status 永远干净、但提交内容明显偏少时，先去看子目录里有没有 .git。

这是一个很容易掉进去、且本地完全看不出问题的坑——只有换机器 clone 时才会爆雷，而那通常是很久以后。养成「add 完顺手 git show --stat 看一眼」的习惯。

接下来

明天进入运维实战靶场的阶段 0：环境准备。第一步是清理宿主机内存——32GB 总量但只剩 3.7GB 空闲，VMware 开不出来。这是整个六阶段路线的第一个阻塞项。

后续会记录 VMware 装法、Host-only 网络配置、三台 VM 创建、免密 SSH 打通的全过程。

如果你也在做内容工程或公开输出，欢迎在评论区交流你遇到过的 git 历史脱敏问题。我用的是 filter-branch（官方已标记不推荐），社区更推荐 filter-repo，想听听大家的实际选择理由。
