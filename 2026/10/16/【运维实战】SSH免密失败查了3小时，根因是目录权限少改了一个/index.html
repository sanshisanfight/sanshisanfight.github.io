【运维实战】SSH免密失败查了3小时，根因是目录权限少改了一个

发表于2026-10-16|更新于2026-10-16|云原生运维
|总字数:2.5k|阅读时长:8分钟|浏览量:

公钥粘贴了，chmod 也执行了，SSH 还是要我输密码

今天搭实验环境，第一台 Ubuntu 虚机装完，配好密钥，想让它免密登录——毕竟后面要批量管三台机器，不可能台台手输密码。

公钥粘贴进 authorized_keys，权限也改了，然后连：

要密码。我明明配了公钥。

第一反应是公钥没写进去，第二反应是换行符不对（Windows 换的公钥，经典的 CRLF 坑），第三反应是 sshd 配置有问题。于是开始一通操作：

三小时，就这么过去了。

后来我干脆把权限全查了一遍，才看见答案：

公钥文件权限完全正确，但它的父目录权限是 755。 而 OpenSSH 要求的恰恰是 ~/.ssh 目录必须 700。

为什么一个目录权限能让公钥彻底”隐身”

这是 OpenSSH 的刻意设计，不是 bug。

SSH 的逻辑是：在读 authorized_keys 之前，先校验它所在目录链的权限。任何一个目录对 group 或 other 有任何权限，SSH 就直接拒绝读这个文件——注意，不是读到了再报错，是根本不读。

所以你看到的现象是：公钥在不在文件里、格式对不对、sshd 死没死，SSH 都不告诉你。它只会给你一句冷冰冰的 Permission denied，因为在 SSH 眼里，你的公钥跟不存在是一回事。

为什么要这么设计：防登录劫持

假设 .ssh 目录对同组或其他用户可写，会发生什么？

任何能进入这个目录的人，都可以往你的 authorized_keys 里追加他自己的公钥。然后你照常输密码登录——但服务端会把你的公钥和攻击者的公钥都拿出来比对，只要有一个匹配就放行。

于是攻击者用他自己的私钥，就能以你的身份登录你的机器。

没有报错、没有痕迹，你甚至不知道自己被登录过。 这就是为什么 SSH 对权限的态度如此强硬：权限不是「安全建议」，是「信任前提」。

三层校验，缺一不可

检查项 要求 违规后果
~/.ssh 目录 700（group/other 零权限） 拒绝读取 authorized_keys
~/.ssh/authorized_keys 600 拒绝
~ 家目录 group/other 不可写（755 或更严） 拒绝
文件属主 必须是该用户本人 拒绝

注意第三行：家目录也不能可写。这是同一个道理——家目录可写，等于别人也能往你的 .ssh 里塞东西。

为什么偏偏是 700

这里有个关键点得想清楚：为什么目录要求 700，而不是 755？

因为 700 = rwx------，其他人连 ls 都做不到，自然更没法在里面创建、修改文件。

如果允许 755（rwxr-xr-x），别人虽然不能直接改文件，但只要有其他方式在该目录里创建文件（比如家目录可写），就能绕过。所以 OpenSSH 直接一刀切：700，一个权限都不给。

顺带搞懂：目录权限和文件权限完全是两回事

排查过程中我犯了个错，正好让我把这件事彻底想明白了。

我当时想「chmod 700 ~/.ssh/ 这个末尾斜杠，是不是只对目录本身生效、对里面的文件无效？」——直觉上觉得这个写法有点怪。决定动手验证一下。

我先手工制造一个错误现场：把文件权限改成 644，然后只对目录执行 chmod：

结论很明确：~/.ssh 和 ~/.ssh/ 完全等价，末尾斜杠只是路径分隔符，没有任何特殊含义。 只有 -R（recursive）才会作用于目录内部。

那为什么不能干脆一把 chmod -R 700 ~/.ssh/ 收工？因为 -R 会把文件也设成 700，多加一个执行位。虽然 SSH 不在意文件多一个 x，但这属于脏做法——权限位该给谁就给谁，不该多给。

目录 vs 文件：同样的 rwx，不同的含义

这才是我一直记混的地方：

权限 作用在文件上 作用在目录上
r 读取文件内容 ls 列出目录里有什么
w 修改文件内容 在目录里创建、删除、重命名文件
x 执行这个程序 cd 进入目录、访问里面的文件

理解了这一点，上面那个「为什么要求 700」就有画面感了：

  • 700 的目录：别人连列出内容都做不到，物理上没法往里塞文件 → 安全
  • 755 的目录：别人能 ls 看到文件列表，虽然不能直接改，但一旦有其他可写路径就能被利用 → 拒绝
  • 600 的目录：能 ls 但进不去，等于废掉 → 这也是为什么没人这么设目录

一句话记忆：对文件，x 是「能运行」；对目录，x 是「能进去、能看到里面」——这是访问的钥匙，不是执行的许可。

这两个覆盖了 95% 的认证问题。 我今天试的 sed -i 's/\r$//' 和改 sshd_config，事后看全是无依据的动作——公钥文件用 od -c 一看就是干净的 LF，PubkeyAuthentication 本来就没被禁用。

判断顺序我总结成四步，以后不再绕：

  1. 用户名对不对？ 报错里的用户名不是你预期的那个，先解决这个
  2. 权限对不对？ stat -c '%a %U:%G' ~/.ssh ~/.ssh/authorized_keys ~
  3. 日志怎么说？ 服务端 journalctl -fu ssh / 客户端 ssh -v
  4. 公钥格式对不对？ 前三步都排除了再看格式

第 1、2、3 步能覆盖绝大多数情况，格式问题实际上排最后——因为它有明确的报错（invalid format），不会像权限问题那样「静默」。

复盘

这次踩坑的本质：我记住了「给 authorized_keys 加 600」，却忘了「.ssh 目录本身要 700」。

关键在于文件权限和目录权限是两套语义，而多数教程只写「chmod 600 authorized_keys」，跳过了目录这一层。跳过的那一层，恰好是唯一会「静默失败」的那一层。

另外今天还顺手搞清楚了一件小事：Windows 上 Git Bash 显示私钥权限是 644，看着像不安全，实际上 chmod 在 NTFS 上不真正生效（走的是 ACL 机制），不影响使用。Git Bash 显示的权限位和 Windows 实际 ACL 是两套东西，别被这个显示值吓到。

今日收获

  1. 权限不对时 SSH 根本不读那个文件 —— 所以它不报错、不提示，只给一句 Permission denied。「没提示」本身就是线索。
  2. 目录权限和文件权限是两套语义 —— x 对文件是「能运行」，对目录是「能进去」。理解了这点，才明白为什么 SSH 要 700 而不是 755。
  3. 别用猜的，用日志的 —— journalctl -fu ssh 和 ssh -v 两件套覆盖 95% 的认证问题。排查的第一件事是拿到证据，不是提出假设。
