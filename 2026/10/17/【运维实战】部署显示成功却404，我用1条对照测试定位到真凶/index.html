hexo deploy 说成功了，curl 却是 404

凌晨把攒了三天的三篇技术文章发到静态站，命令跑得干干净净：

deploy 打印了 commit 区间，没有报错，退出码 0。从运维直觉看，这事成了。

顺手 curl 一下新文章验证——

第一反应是：部署失败了。手都已经在 hexo clean 上了。

排查：先别急着重推

冷静下来，把假设列出来。404 只有三种可能：

假设 如果成立，应该看到什么
A. 部署失败，文件没推上去 首页也是 404 / 站点打不开
B. 文件在，但 URL 拼错了 首页正常，老文章 URL 正常，只有这个 404
C. Pages 构建延迟，线上还没更新 首页正常，但首页里找不到新文章链接

三条假设，三次测试就能切开。第一步测首页：

假设 A 死了。 站点活着，部署没整体失败。

第二步是这次排障里最值钱的一步——设对照组：

老文章也 404。 这一下把假设 B 也砍掉了——如果是我这次拼错了新文章的 URL，没道理把老文章的 URL 也拼错；如果真是 URL 编码问题，那两个标题都有全角括号，都有中文，都得编码。

现在的可能性只剩 C：URL 编码 + 构建延迟。

根因一：percent-encoding，手拼 URL 的头号杀手

中文和全角标点进URL 路径必须做 percent-encoding。问题是它是逐字节的十六进制转义，肉眼完全没法校验。

我那个标题 【运维实战】SSH免密失败查了3小时，根因是目录权限少改了一个，真实的编码结果长这样：

注意 【 是 %E3%80%90，，（全角逗号）是 %EF%BC%8C——全角标点也占编码位，一点都不比 ASCII 便宜。手拼这种串，错一个百分号、少一个字节，curl 不会警告你，它只会老老实实返回 404。

curl 不校验你的 URL 拼得合不合理。 这是这个坑最阴的地方。

根因二：Pages 是异步构建，push 完成 ≠ 线上可访问

GitHub Pages 的模型是：你 push 到 <user>.github.io 仓库 → 触发一个 webhook → GitHub 服务端拉取分支、构建、缓存 → 对外提供服务。

这中间有1 到 3 分钟。这期间仓库里有文件，但线上还是旧版本。

所以「deploy 命令成功」和「线上能访问」是两件独立的事，必须分开验证。很多人的 deploy 脚本跑完就宣布成功，然后被自己骗一次。

顺手记一笔：git remote 为空 ≠ 发不出去

排查过程中还有个小误判值得提一嘴。

看 git remote -v 是空的，我一度以为这套发布方式走不通。完全不是这回事。

Hexo 是双仓库结构：

仓库 装什么 干什么
源码仓库 source/ + themes/ + _config.yml 管版本历史、备份、多设备同步
Pages 仓库 public/ 全量静态文件 管线上访问，GitHub Pages 唯一认的东西

hexo deploy 读的是 _config.yml 里的独立 deploy: 段：

由 hexo-renderer 的 git 插件直接 push 到 Pages 仓库，完全不经过源码仓库的 remote。

所以判断口诀是：remote 为空不影响 deploy，先看 deploy: 段配没配。 把「git push 到源码仓库」和「hexo deploy 到 Pages 仓库」混成一件事，就会得出这种荒谬结论。

复盘：对照组是排障里最便宜的工具

这次排障真正值钱的不是 percent-encoding 的知识，是那个多测一条老文章 URL 的动作。

面对一个失败的观测，人的本能是「改改看」——重推一次、清缓存重来、改配置。而正确的第一反应应该是：造一个能区分假设的测试。

  • 只测新文章 404 → 问题空间是「部署链路 × 编码 × 缓存」三维
  • 加上老文章 404 → 砍掉一半，直接收敛到「编码 × 缓存」

一条 curl 的成本几乎为零，但它排掉的是一整个错误排查分支。如果当时直接 hexo clean 重推一遍，我会重写一遍正确的东西、然后继续拿到 404，并且更确信「是不是 Pages 坏了」。

具体的判断方法（可以迁移到任何 404 / 连不上 / 读不到的场景）：

  1. 先测最外层 —— 服务本身活着吗？首页/健康检查能通吗？不通就别看细节了
  2. 再设对照组 —— 一个「已知正常的同类目标」能访问吗？不能 → 问题在公共链路；能 → 问题在具体目标
  3. 最后才测自己的东西 —— 此时问题空间已经很小了
  4. 别手输标识符 —— 任何带编码、动态后缀、哈希、长数字串的 URL，一律从上游数据源提取原文

第 4 条是通用原则，不只针对中文标题：token、对象 ID 带哈希、URL 有查询参数编码，道理完全一样——手拼的永远不如提取的可靠。

今日收获

  1. 「命令成功」和「服务可用」之间隔着一个异步构建。部署类操作的成功判据不是命令退出码，是从目标端读回来的真实响应。
  2. percent-encoding 是脚本化验证的头号障碍。别拼，去 HTML 里 grep 真实链接 —— 这一招顺便让验证脚本变成可重复执行的自动化步骤。
  3. 排障的第一步永远是砍假设，不是动手改。一个对照测试的边际成本极低，但它砍掉的分支可能要你重推三次。
