【运维实战】VM 配了 8GB 内存，宿主机却只占 5.59GB，我才发现它偷跑了 3.8GB

发表于2026-10-19|更新于2026-10-19|云原生运维
|总字数:3.2k|阅读时长:12分钟|浏览量:

一台”只用了一半”的虚拟机

昨晚我发现那台练手用的 Ubuntu 虚拟机还在跑着——Get-CimInstance Win32_Process 里 vmware-vmx.exe 赫然在列，常驻内存 5.59 GB，是我这台机器上占用最高的进程。

第一反应是：还好我只开了 8GB 的 VM，没开三台，不然 31.8GB 的内存肯定不够用。

然后我顺手去翻 vmware.log，想看看它今天有没有什么异常。日志末尾全是些看不懂的 MemSched 记录，我本来打算关掉就走，余光扫到一行：

swapped 1002206。

Linux 的内存页大小是 4096 字节，1002206 × 4KB ≈ 3.83 GB。

这台 8GB 的虚拟机里，有 3.83GB 已经被换出去了。

而宿主机任务管理器上，我只能看到它占了 5.59GB。

一个 8GB 的东西，只占了 5.59GB，差的那 2.4GB 去哪了？而 VM 内部又有 3.83GB 在换页？两个数字对不上，而且都很不合理。 那天晚上我就决定把这事查清楚——因为后面我还要在这台 VM 上跑 K8s，如果内存账本本身就是错的，那我后面所有的容量规划都是拍脑袋。

排查过程

第一步：先分清”物理内存”和”提交量”

Windows 上有两个内存指标，长得像，含义完全不同。看错指标是后面所有误判的源头。

提交上限 61.5GB = 物理内存 31.8GB + 页面文件，这个差值就是超卖的额度。

第二步：找出真正吃内存的进程

输出（节选）：

vmware-vmx 排第一，5.59GB。

第三步：去 VMware 的日志里找真相

这一步有个小陷阱，我踩了。

vmware.log 里的时间戳是 UTC，不是本地时间。日志头部就写着：

我按本地时间去 grep 2026-10-19T1[3-9]（下午），结果一条都没捞到，一度以为 VM 今天没运行。改成按 UTC 找 2026-10-19T(13|14|15) 才命中——本地 21:00–23:00 对应 UTC 13:00–15:00。

正确判断 VM 是否在跑，别猜时间，直接看日志首尾时间戳的跨度：

结果是日志从 10-16 02:18 一直连续写到 10-19 14:51（UTC）——这台 VM 已经连续运行了 3 天 13 小时，一次都没关过。

第四步：读懂 MemSched 那行日志

把噪音（lib/ssl 那些加密套件协商）滤掉，只看内存调度：

关键的一行拆开看：

字段 数值 含义
target 2146595 页 ≈ 8.0 GB VM 配置的内存上限（正好是配的 8GB）
locked 1098019 页 ≈ 4.19 GB 当前被锁定的页
balloon 0 当前气球回收量为 0
swapped 1002206 页 ≈ 3.83 GB 已被换出的内存
minmempct 50 宿主机至少要给 VM 留 50% 的时间片

target 是 8GB，和我配的完全一致——VMware 确实按 8GB 在算账。 但 swapped 显示其中 3.83GB 实际已经不在内存里了。

同时还有一行：

Balloon enabled 1 —— 气球驱动已启用。

根因：两套换页机制叠加，把内存账本搞乱了

VMware 侧的内存气球（Ballooning）

VM 里装了一个叫 vmware balloon driver 的驱动。宿主机内存紧张时，宿主机会主动从这个驱动里”拔气球”——把 VM 内部的内存页收回来给宿主机自己用。

日志里 Balloon enabled 1 说明这个机制是开着的。设计意图是自保：宿主机快满了，先从 VM 里榨一点出来，总比让宿主机自己崩掉强。

Linux 侧的应用换页

VM 里跑的是 Ubuntu，是个完整的操作系统，它有自己的内存管理。Linux 会把很久没访问的冷页面换到自己的 swap 里。

两个机制叠在一起，就成了今天这个局面

结果就是宿主机和 VM 两边的内存数字完全对不上：

  • 宿主机任务管理器说：vmware-vmx 只用了 5.59GB
  • VMware 日志说：VM 目标 8GB，其中 3.83GB 已换出
  • 8 − 3.83 ≈ 4.2GB → 和宿主机看到的 5.59GB 是能对上的（加上气球页和其他开销）

关键认知：memsize = 8192 只是”许可额度”，不是”实际占用”。 VM 内部认为它有 8GB 可用，但其中约一半已经在磁盘上了。这时候你在 VM 里面跑 K8s、跑 ES、跑一堆中间件，宿主机上看到的内存曲线会严重低估 VM 的真实压力——这就是容量规划失真的根源。

那”为什么 VM 只跑了一个还这么卡/这么紧”

因为这 3.83GB 不是我主动换出去的，是宿主机内存不够，VM 被迫交出去的。我之前把 8GB × 3台 = 24GB 和 31.8GB 一减，觉得”差 8GB，挤一挤总能跑”，这个算法错在没算宿主机自己也要吃内存：

项目 占用
物理内存总量 31.8 GB
Windows 系统自身 + 常驻程序 约 6 GB
Defender / 压缩 / 内核池等系统开销 约 3 GB
VMware 进程本体 约 1 GB
留给 VM 的实际空间 约 20 GB

而且这 20GB 还要同时容纳三台 VM。内存一紧张，气球就开始回收，VM 内就开始换页——机器就进入了”账面够用、实际卡顿”的薛定谔状态。

解决方式

治标：立刻把内存还回去

第一步，关掉不用的 VM（这是回血最快的一步）

在 VMware GUI 里正常关机（别直接杀进程，会丢数据）。一台 8GB VM 关掉，宿主机立刻回收约 5.6GB。

第二步，卸掉冗余的虚拟化软件

我测试机上同时装着 VMware 和 VirtualBox，两个软件的虚拟网卡会互相抢网段：

卸掉 VirtualBox 能一次性解决两件事：释放内存 + 释放它占着的网段。

治本：别让 VM 配置超出宿主机能力

重新定规格，让账算得过来：

方案 每台 VM 三台合计 是否可行
原计划 4C8G 24 GB ❌ 超出约 20GB 可用额度，必然换页
降规格（推荐） 2C4G 12 GB ✅ 留足余量，K8s 单节点也够
换宿主 — — 扩到 64GB 或改用 ESXi / 云主机

关掉不需要的内存大户（按实测收益排序）：

我这台机器上 vmware-vmx(5.59) + Memory Compression(1.33) + QQLive(1.04) + WorkBuddy(0.82) + MsMpEng(0.56) + 微信开发者工具(0.54) + 百度网盘(0.84) —— 关掉几个娱乐和开发工具，收益比想象中大。

监控常态化，别等卡了才看：

复盘与延伸

通用判断方法：虚拟机内存排查的三板斧

遇到”虚拟机内存不对”，按这个顺序查，不要跳步：

第一斧——先分清是宿主机紧还是 VM 紧

  • 物理占用低但提交率高 → 有大量内存被申请但没落实，检查页面文件和超卖
  • 两个都高 → 真的不够用，必须做减法

第二斧——去 vmware.log 读 MemSched，别只看任务管理器

重点看三个字段：target（配置额度）、swapped（已换出）、Balloon enabled（气球状态）。

第三斧——进 VM 看 free -h 和 vmstat

free -h 里 available 这一列已经把缓存和换页影响算进去了，比 free 那列有参考意义得多。

三个容易踩的坑

1. memsize 不是占用量，是许可额度。

这是最根本的认知错误。看到”配了 8GB”就以为它占 8GB，或反过来以为”只显示 5.59GB 那是安全的”——两个方向都错。

2. 日志时间戳可能是 UTC。

vmware.log、很多系统日志都这样。查日志前先看头部有没有 offset from UTC 声明。查不到就两个都试，或者直接看日志首尾跨度判断”有没有在跑”，比猜具体时间靠谱。

3. 终端显示乱码 ≠ 文件损坏。

我看到 .vmx 配置文件里磁盘文件名显示成乱码，以为文件坏了。用 od -c 一看，字节是 316 273，就是 UTF-8 的「位」字，磁盘上真实文件名完全正常，只是 Git Bash 终端按错编码显示了。

千万别因为终端乱码就去”修复”文件名——那才是真制造故障。

今日收获

1. 虚拟机的内存账本要查三层，任务管理器只是一层。

宿主机进程内存 → vmware.log 的 MemSched → VM 内 free -h。只看第一层，容量规划就是拍脑袋。

2. “配了 8GB”和”占了 8GB”之间，隔着一个气球驱动和一整个宿主机。

Balloon enabled 1 这五个字母，比任何配置文档都更能解释”为什么我的 VM 这么卡”。

3. 容量规划要把宿主机的开销先扣掉。

31.8GB 不等于能给 VM 31.8GB。先扣系统、扣软件本体、留 20% 余量，剩下的才是 VM 的可用额度。 我今天就犯了这个错——把 31.8GB 当成了全部可用。

如果你也在用虚拟机做测试环境，别再相信任务管理器上的数字了。 花两分钟读一下 vmware.log 里的 MemSched，你会看到一个完全不同的内存真相。

有没有遇到过”虚拟机配的内存明明够，却莫名其妙变卡”的情况？评论区聊聊你的排查思路。
