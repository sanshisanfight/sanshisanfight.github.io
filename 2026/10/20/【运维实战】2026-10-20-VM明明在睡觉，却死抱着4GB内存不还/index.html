【运维实战】VM 明明在睡觉，却死抱着 4GB 内存不还，根因是一个叫 minmempct 的地板

发表于2026-10-20|更新于2026-10-20|云原生运维
|总字数:3.3k|阅读时长:11分钟|浏览量:

昨天我写了一篇《VM 配了 8GB 内存，宿主机却只占 5.59GB，我才发现它偷跑了 3.8GB》。

写完当天晚上我就觉得自己哪里不对，于是今天把那个 MemSched 日志逐个字段拆开重算了一遍。

结论是：我昨天写错了。 那 3.8GB 不是宿主机在丢内存，是虚拟机自己关起门来在内部倒腾。而今天真正值得写下来的，是另一个完全不同的问题——

这台虚拟机明明在睡觉，却死抱着 4.19GB 宿主机内存，一GB 都不肯还。

一、现象：一台”什么都没干”的机器，内存占用第一

先摆数据。这台 VM 配了 8GB 内存（memsize = "8192"），宿主机构建之后一直开着没关。

看内存占用排名，vmware-vmx 稳坐第一：

物理内存 31.8 GB，可用只剩 4.0 GB，占用率 87.4%。提交量 51.45 GB / 上限 61.5 GB = 83.6%。

按理说，我昨天已经确认了这台机器”连续运行 3 天多没关”。一台闲置的虚拟机占着 4GB，合理， shut down 就完事了。

但今天我突然想到一个问题：它真的在闲置吗？

三方交叉验证

我用了三个互相独立的角度去验证这台 VM 到底在不在干活：

角度一：CPU 实时占用

输出：

开了4 天 12 小时，累计只用了0.5 小时满负荷 CPU 当量。折算下来平均使用率不到 0.5%。

角度二：虚拟磁盘写入量

如果 VM 内部在换页，必然要写虚拟磁盘。间隔 30 秒量两次：

输出：

零字节写入。 一个正在换页的虚拟机，磁盘写入量不可能是 0。

角度三：页面文件趋势

输出：

页面文件已经从峰值 8.3 GB 回落到 3.6 GB，说明系统主动把换出去的东西收回来了，不是持续恶化。

三个角度指向同一个结论：这台 VM 真的在睡觉。

二、排查：那它到底占了宿主机多少内存？

这里就要说到关键工具了。

VMware 的运行日志 vmware.log 里有一行 MemSched，记录了气球驱动（balloon driver）的实时状态。这行信息密度极高，大部分人只看到一半就下结论了——我昨天就是。

先说清楚这个日志的时间戳问题：vmware.log 里的时间是 UTC，比本地慢 8 小时。 判断 VM 跑了多久，要看日志首尾时间戳的跨度，不是猜具体时间点。

输出（两条，分别取自前一天和后一天）：

Linux 页大小 4KB，所以换算公式是 字节 = 页数 × 4096，GB = 页数 × 4096 / 1024³。

逐字段拆开：

字段 页数 换算 含义
shares 2097152 8.00 GB 配置值（对应 memsize = "8192"）
max 2146595 8.19 GB 允许上限
min 1098019 4.19 GB 气球回收地板
locked 1098019 4.19 GB 当前实际锁定
target 2146595 8.19 GB 目标值（未达成）
swapped 1002253 3.82 GB VM 内部 Linux swap
touchedPct 0 — 被访问过的内存页比例
dirtiedPct 0 — 被写过的内存页比例

关键就在这一行

两个数字完全相等。

这意味着：气球驱动已经把内存戳到回收地板了，再也戳不动了。

而且 locked 换算出来是 4.19 GB，和任务管理器里 vmware-vmx 的 4.15 GB 几乎完全吻合——这 4.19 GB 才是真正占在宿主机物理内存里的部分。

再看这两个：

被访问的内存页比例 0%，被写过的内存页比例 0%。 这是 VMware 自己给出的直接证据：这台虚拟机一个页面都没碰过。它确实在睡觉。

地板线是哪来的？

日志里还有一条：

验算一下：min / shares = 1098019 / 2097152 = 52.4%。

配置 50%，实际算出 52.4%（多出来的是少量管理开销），完全对得上。

三、根因：minmempct 是气球驱动的人格底线

气球驱动是怎么工作的

虚拟机跑在宿主机上，靠一个叫 vmware-vmx 的进程。宿主机内存紧张时，VMware 会在虚拟机内部撑起一个”气球”，然后往气球里灌气，把虚拟机的内存页挤出来还给宿主机。

这个机制叫气球驱动（Balloon Driver），对应虚拟机内部那个驱动在Linux 里会显示成一个叫 virtio_balloon 的设备。

理论上，只要虚拟机不用内存，气球就能一直戳，把内存全部抽干。

但 VMware 留了个后门。

minmempct：内存的人格底线

minmempct 是 VMware 的一个配置项，全称是 minimum memory percentage——虚拟机内存被回收的最小百分比。

它的语义是：无论宿主机内存多紧张、多缺，虚拟机内存最多只能被气球抽走 minmempct 指定的那个比例，剩下的必须原样留着。

今天的配置是 50，意思是：最多抽走一半。

于是就有了这个结果：

为什么”空闲”反而”占得更多”

这个机制导致一个反直觉的现象：

虚拟机越空闲，越显得占着茅坑不还。

因为空闲的 VM 不产生内存压力，虚拟机的”真实需求”远低于 8 GB。VMware 完全可以在气球回收时顺手把闲置内存抽走——但 minmempct 50 明确禁止它这么做。

所以现在的局面是：

  • 宿主机：内存紧张，可用只剩 4.0 GB
  • 气球：已经戳到地板，无能为力
  • VM：闲着，CPU 0.52%，磁盘零写入，touchedPct 全0
  • 结果：各占 4.19 GB，谁也动不了

四、顺手更正一下我昨天的错误结论

昨天那篇文章我写的是「VM 偷跑了 3.83GB 内存」，还言之凿凿地分析了「双层换页导致账本失真」。

今天把字段拆开之后，发现我把账算错了。

看 swapped 这个字段，1002253 页 = 3.82 GB。昨天我把它当成了「宿主机正在丢的内存」，还专门去查了宿主机页面文件做交叉验证。

问题在于，swapped 反映的是虚拟机自己内部的 Linux swap，不是宿主机内存。

虚拟机的内存有三本账，混在一起就会得出荒谬结论：

账本 对应字段 存在哪 宿主机看得到吗
虚拟机占宿主机多少 locked 宿主机物理内存 ✅ 看得见（就是 vmware-vmx 工作集）
虚拟机内存的边界 min/max/shares 配置值 —
虚拟机内部 swap swapped 虚拟磁盘里 ❌ 看不见

昨天我盯着第三本账，把它当成第一本账。swapped 大，只说明 guest 自己觉得内存不够用，跟宿主机丢不丢内存是两回事。

再补一个数据：两天的 swapped 对比——

一天只增加了 47 页 = 188 KB。基本冻结。 根本不存在昨天文章里说的「持续恶化」。

五、解决方式

方案一：关掉闲置的 VM（最直接）

收益最直接——把 vmware-vmx 干掉的瞬间，4.19 GB 原封不动全回来。

方案二：把 minmempct 调低

如果你希望 VM 在闲置时能主动归还更多内存，改这个参数：

或者通过 vmware-vdiskmanager / VMware GUI 的虚拟机设置里调整内存预留策略。

不过要提醒一句：调低地板线会让 VM 在宿主机紧张时被”抽得更狠”，性能抖动风险上升。 实验室环境够用，生产环境要谨慎。

方案三：重新规划 VM 规格（治本）

今天的实测给了新的判断依据：

8 GB 配置在 31.8 GB 宿主机上，会让气球长期顶在地板线。 因为宿主机的物理内存要留给 Windows 自己（约 6 GB）加上各种常驻软件（约 4 GB），真正能分给 VM 的只有 20 GB 左右。

按这个数算，三台 VM 每台 8 GB = 24 GB，必然超卖。

改成 2 核 4 GB：

  • 三台合计 12 GB，留足余量
  • 地板线只有 2 GB，宿主机压力显著缓解
  • K8s 单节点跑实验集群，4 GB 够用

六、复盘：这类问题怎么快速判断

方法一：抓 locked == min 这个等式

这是今天最有效的一条。跑一遍：

对比 locked 和 min：

  • locked == min → 气球已到底线，宿主机再缺也抽不动了
  • locked < min → 还有回收空间

这个等式能一句话说清「为什么 VM 空闲着还占内存」，比看十个性能计数器都有用。

方法二：touchedPct / dirtiedPct 判断真假空闲

这两个字段是 VMware 自己给的权威答案，比在宿主机上看 CPU 靠谱得多。

宿主机 CPU 会被微信、QQ 直播、网盘同步搅成一锅粥，分不清是 VM 在忙还是别的进程在忙。但 VM 内部有没有碰过内存页，VMware 自己最清楚。

方法三：先分清是哪本账

任何时候想看「VM 占宿主机多少内存」，答案永远是 locked，不是 swapped。

我昨天就是在这上面翻的车。以后看到任何内存数字，先问一句：这个数字是宿主机物理内存，还是 guest 内部 swap，还是配置文件里的规划值？

七、今日收获

1. 虚拟内存有三本账，看错任何一本都会得出错误结论。

宿主机物理内存（locked）、虚拟机内存边界（min/max/shares）、虚拟机内部swap（swapped）——三者物理位置不同，混在一起算必然出错。我昨天就栽在这一条上。

2. minmempct 决定了气球能戳到多低，也决定了「空闲 VM 的内存地板」有多高。

配 8 GB + minmempct 50 = 地板线 4 GB。这意味着这台 VM 在任何情况下都至少占 4 GB，哪怕它一周不开机。容量规划时必须把这个地板算进去。

3. 判断「VM 是不是真在干活」，touchedPct 和 dirtiedPct 比任何外部监控都直接。

这两个字段是 VMware 自己的记账，没人能造假。今天它们都是 0，配合 CPU 0.52%、磁盘 30 秒零写入，三方互证得出「真在睡觉」的结论——比在任务管理器里瞎猜强得多。

4. 昨天写错的结论今天必须改，这比写对更重要。

昨天那篇文章发出去的时候数据是错的。技术博客最怕的不是「没写」，是「写错了还写得很确信」。发现自己的错并明确推翻，比多写一篇正确的新文章更有价值。

顺便说一句： 这台 VM 现在还开着，因为它没有密码登录通道——SSH 免密连着两天挂了，而 VMware 控制台需要手工操作。这大概是「一台机器没人管的时候会发生什么」的最好示范：它会安静地、以一种看起来很合理的方式，浪费掉你四分之一的物理内存。
