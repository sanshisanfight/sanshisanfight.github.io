【运维实战】权限明明是700，SSH还是拒绝我，根因是stat只看了终点

发表于2026-10-21|更新于2026-10-21|云原生运维
|总字数:2.4k|阅读时长:8分钟|浏览量:

stat 说 700，sshd 说不对 —— 到底听谁的？

那天晚上我盯着这台机器已经两个小时了。

权限完美。属主正确。authorized_keys 是标准的 600。

我接着排查了所有能想到的地方：公钥内容是不是复制错了？没有。文件有没有 CRLF？没有。sshd_config 里 PubkeyAuthentication 是不是 yes？是。sshd 服务状态？active (running)，Server listening on 0.0.0.0 port 22。密钥指纹跟客户端 ssh-add -l 出来的对得上。

全部正常。

但连接依然被拒：

stat 说 700，sshd 说不对。矛盾。

后来我加了一条命令，真相才浮出来——而它跟权限本身几乎没关系。

一、决定性证据不在权限里，在日志里

权限排查最大的误区，是一直在权限上找答案，却不看系统到底在抱怨什么。

sshd 把拒绝理由写得清清楚楚，只是没人去看：

好，那这句话说 .ssh 权限不对。回到 stat——700，没问题啊？

注意这里有个关键点：报错说的是「owner ship or modes」，而且它给的是一条路径，不是权限值。

sshd 并没有告诉你「期望多少」，它只是说「我检查的这条路径上，有东西不对」。

这时候继续调 .ssh 本身的权限，是在解一道根本没有答案的题。

中途插曲：一次重启引出的二次困惑

排查过程中我试过systemctl restart ssh，结果撞上另一个报错：

systemd 限流了。删掉 StartLimitBurst 又试了几次，全是这句。

这是本次排障里最误导人的一段——报错信息从「权限不对」变成了「起不来」，注意力自然被带偏了。

后来我用了个笨办法：把 systemd 的前置检查手动跑一遍。

哦，是 host key 缺失。ssh-keygen -A 重新生成后，服务正常启动了。

但服务起来之后，认证还是被拒。「服务起不来」和「认证被拒」是两个独立问题，把它们混在一起会浪费大量时间。这是本次踩的第二个坑。

所以正确的顺序是：

sshd -t 一条命令输出 no hostkeys available -- exiting，比反复 restart 三次有效得多。

二、一条命令看到真相：namei -l

sshd 报错提到的是「路径」，那就把整条路径打出来。

namei 这个命令的作用是逐级解析路径上每一级目录的权限和属主：

.ssh 是 drwxrwxrwx。777。

所有人对所有人可写。

三、可是 stat 明明显示 700。谁在说谎？

没人说谎。这是本次排障最值得琢磨的地方。

stat 和 namei 都是如实汇报的，它们只是回答了不同的问题：

命令 回答的问题 不回答什么
stat 执行那一刻，这个 inode 的 mode bits 是多少 路径链上级；ACL；扩展属性；文件系统类型
namei -l 从根目录到目标，每一级的权限与属主 单个 inode 的 ACL 与扩展属性

那为什么两次读到的值不一样？

因为它们读的不是同一时刻。

namei 前面，我为了验证「是不是权限问题」，做过一次这样的操作：

这行输出是误导的来源。实际情况是：执行到这一行时权限确实是某个值，但我在前后又改过。

教训一：stat 显示正常 ≠ 权限真的正常。
它读的是执行那一刻的快照。任何在此之前或之后的改动，都能让这个数字失效。

而且，stat 就算读到的是「真实的当前值」，它依然可能是骗人的。因为它看不到四类东西：

隐藏因素 用什么查 症状
ACL 额外授权 getfacl ls -l 权限串末尾有 + 号
immutable / append-only lsattr chmod 返回成功但文件纹丝不动
路径链上级目录权限 namei -l 就是今天这个坑
fuse 挂载 df -T chmod 返回成功但完全无效

fuse 挂载是最阴的一种。VMware 共享文件夹、sshfs、部分 overlayfs 都属于这一类——它们不支持 chmod，但命令不报错。很多人对着它改了一下午权限，方向从一开始就是错的。

教训二：权限排障第一步是 namei -l，不是 stat。

四、根因机制：StrictModes 查的是整条路径，不是一级

回到最开始那句报错：

我当时最大的误解，是把它读成了「/home/ops/.ssh 这一级的权限不对」。

它是检查的终点，不是问题所在的那一级。

OpenSSH 的 StrictModes yes（默认值）开启后，认证前会遍历从 / 到 authorized_keys 的每一级目录，逐级检查两件事：

  1. 属主是否合法 —— 必须是 root 或该用户本人
  2. 是否对 group / other 可写 —— 如果别人能改，就能做中间人攻击

任何一级不满足，整个认证直接拒绝。

判断口诀：从下往上看，每一级都要问「别人能不能改它」。

层级 期望
/ root:root，other 不可写
/home root:root，other 不可写
家目录 本人属主，755 或 750
.ssh 700
authorized_keys 600
ACL 无额外 user 条目
扩展属性 无 i / a
文件系统 不能是 fuse / vmhgfs

而 stat 只看最后两行。它压根没有能力告诉你「/home/ops 是不是 777」。

五、解决：先定位，再一次性修对

第⑤ 步是关键——既然 StrictModes 查的是整条链，就必须整条链一起修。 只修 .ssh 这一级，如果 /home/ops 也是 777，照样被拒。

六、复盘：这个坑的通用判断方法

1. 服务报错信息里藏着最精确的线索

sshd 的日志已经把「哪条路径」告诉你了。别猜，去读。

这句话本身没说期望值，但「路径」这个信息极其宝贵——它告诉你该用 namei -l 而不是继续敲 stat。

2. 「我全查过了都是对的」是危险信号

当你确认配置、权限、内容、服务状态全部正常，但问题依旧，说明你的检查工具存在盲区，而不是问题不存在。

这时候该做的不是继续加深同一类检查，而是换一个视角的工具。今天从 stat 换到 namei -l，一次就结束了。

3. 排查过程中不要污染现场

我那次 chmod 777 是为了「验证是不是权限问题」，但它污染了现场——让后续读取全部失真。

更稳的做法：先只读不改。 用 namei -l / getfacl / lsattr 把状态看清楚了，确认要改哪一级，再动手。

4. 换发行版要重新检查默认机制

这台机器后来换成了 Rocky Linux，同样的 SSH 问题，权限 600 全对，依然连不上：

SELinux 给 /root/.ssh 要求一个特定的安全上下文（ssh_home_t）。文件权限对了，但上下文不对，SSH 一样拒绝。

Ubuntu 上不存在这个坑。 这类「一个发行版有、另一个没有」的默认机制，是排查环境差异时最容易被忽略的一层。

今日收获

1. stat 是快照，namei 是全貌。 权限排障的第一步应该是 namei -l，因为它能同时告诉你「路径链」和「当前值」这两件事，而 stat 只能告诉你后者。

2. 报错里的路径是检查终点，不是罪魁祸首。 StrictModes 遍历整条链，任何一级不对都归到同一个报错上。看到「某目录权限不对」时，要做的是查整条链，不是死磕那一级。

3. 当所有检查都「正常」时，先怀疑工具的盲区。 stat 看不到 ACL、扩展属性、路径链上级、fuse 挂载。换工具比加深检查有效得多。

这个坑我前后折腾了五天才定位到根因。中间有两段时间我甚至以为「配置全对但就是连不上」是玄学。

后来复盘的时候才明白：不是玄学，是我在用一把只能看见表面数字的尺子，去量一个三维的问题。

stat 就是那把尺子。它没坏，它只是不够长。
