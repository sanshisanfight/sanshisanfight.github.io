【运维实战】200 行日志统计全对，uniq 却只认「相邻」不认「相同」

发表于2026-10-22|更新于2026-10-22|云原生运维

学生说「我不会 awk」，我第一反应是：那就别用 awk

昨天在 Linux 基础练习里留了一道题，题目很朴素：

分析 Web 访问日志，找出访问次数最多的客户端 IP，把结果写入 top.txt。
日志第 1 列是 IP。

题面给的提示是 awk '{print $1}' 和 sort | uniq -c。

交上来的心得文件里，用户写道：

第三题有点难了，没怎么用过 awk，我看了菜鸟教程，awk 的用法，还是卡在了，如何识别相同的 IP，并计算相同行数，还要最大的，再输出第一列的 IP 地址。

我第一反应是：这是典型的「命令都会用，但不会串起来」，讲一遍管道组合就通了。

但我去机器上一跑，发现不对。

排查过程

第一步：先看数据长什么样

练习环境在 Rocky 9 上，日志是脚本生成的 Apache 格式，200 行。

看起来很正常。

第二步：跑标准答案

没问题。200 行，5 个 IP，计数完全对得上。

第三步：跑「错误答案」—— 结果是全对的

uniq 有个 notorious 的特性：它只统计相邻的重复行，不做全局去重。
所以 sort 是它能工作的前提。少一个 sort，结果应该是乱七八糟的。

我按这个认知跑了一遍漏掉 sort 的版本：

和标准答案一模一样。

我盯着这个输出看了几秒。一个理论上会错的解法，在我的练习数据上给出了完全正确的答案。

这不可能是巧合。

第四步：找到数据生成器

答案在生成日志的脚本里：

每个 IP 的行是连续写出的。 先一口气写 70 行 .50，再写 20 行 .50，然后才轮到 .80。

这份数据天生就是「已排序」的。

第五步：打乱数据做对照实验

这是整个排查里最关键的一步。怀疑是数据的问题，就用 shuf 把顺序打乱，让真相自己浮出来：

全是 1、2、3 的碎片。 漏掉 sort 的解法立刻崩塌。

再补上 sort，无论数据怎么打乱，答案都稳定正确：

对照实验做完了，结论很清楚。

根因：两个东西叠加在一起

表层：uniq 是流式算法，不是集合算法

uniq 的实现方式是逐行流式比较：读入一行，跟内存里保留的上一行比。
不一样就输出，一样就计数加一。

注意它没有排序。它眼里只有「上一行」和「这一行」，
所以它只能识别连续出现的相同内容，对隔了一行的相同内容完全无感。

这就是为什么 sort 不是可选项，而是 uniq 能工作的前提条件：
sort 把散落各处的相同内容搬到一起，制造出「相邻」这个前提。

深层：我的数据生成器把前提条件给满足了

gen_line 按 IP 连续写入，产出的是天然有序的数据。
于是：

解法 在我的题库上 在真实乱序日志上
uniq -c（漏 sort） ✅ 全对 ❌ 全是 1
sort | uniq -c | sort -rn ✅ 全对 ✅ 全对

错误解法在练习数据上蒙对，在生产环境上崩塌。

更要命的是第三层：这个坑是我自己造的。
我写数据生成脚本的时候，只想着「造一份看起来像样的访问日志」，
完全没意识到数据的排列顺序本身就是一道隐含的考题。
我亲手把「sort 存在的意义」这个知识点从题库里删掉了。

更微妙的是，这种「假数据」不会立刻暴露问题。
学员在题库上做对了 → 拿到满分 → 觉得学会了 → 换到真实日志上翻车。
错误的思维习惯，要到生产环境才第一次付出代价。

解决方式

立刻修数据：给日志加乱序

在 setup.sh 生成完日志之后，加一步打乱：

shuf -o 文件 文件 是原地打乱，GNU coreutils 自带。
Rocky / Ubuntu 都不用装任何东西。

改完之后必须验证错误解法确实会错：

记成固定套路：统计三件套

不管统计什么，sort 永远是第一步：

注意这里有两个 sort，它们干的是完全不同的活：

位置 作用 去掉会怎样
第一个 sort（uniq 前） 把相同内容搬到一起，制造「相邻」 uniq 失效，计数全是 1
第二个 sort（uniq -c 后） 把计数结果按数值倒序排 只能得到并列第一，不是 TOP 榜

去掉任何一个都不行。这是最容易只记一半的地方。

复盘与延伸

延伸一：IP 排序还有第二个坑 —— 字典序 vs 数值序

即使 sort 加上了，默认的 sort 也是字符串比较：

.100 排到了 .9 前面。要按 IP 的真实大小排，必须指定分隔符和字段：

  • -t. —— 以 . 作为字段分隔符
  • -k4,4n —— 按第 4 段，数值比较（n = numeric）

做 TOP N 榜单时，计数用 -rn 就够了；但如果你要输出的是按 IP 排序的清单，这个坑必须知道。

延伸二：awk 也能做，但别默认上 awk

用户卡住时第一反应是「我不会 awk」，然后去啃 awk 教程。
其实这道题 awk 完全写得出来：

c[$1]++ 是一句话的事：用数组当哈希表做累加。

但两者的取舍很清楚：

sort | uniq -c awk
可读性 高，三个动作一目了然 需要懂 awk 语法
性能 有排序开销 一次扫描，大数据量更快
适用 通用，Shell 面试高频 字段处理复杂、需要条件判断时

能用管道说清楚就别上 awk。 管道是 Shell 的通用语，awk 是另一门语言。

延伸三：这条经验本身可以推广 —— 别相信「假数据」

shuf 打乱做对照实验，这个手法不只能用在日志上。

任何时候你怀疑「某个操作是多余的」，就把输入顺序打乱再跑一遍。
如果结果变了，说明那个操作确实在起作用，之前的「看起来多余」是数据顺序给的假象。

反过来说：如果你发现某个知识点「怎么写都对」，第一个该怀疑的不是自己太笨，而是你的测试数据太配合。

延伸四：顺带一提，同一份日志还暴露了另一个运维大忌

同一天的练习里还有第 5 题，要求把「进程名 + PID」写进文件。
用户的答案是：

数字是查出来抄进去的。进程一重启 PID 就变，这行记录立刻变成垃圾。

正确做法是命令替换，让系统每次执行时自己取实时值：

$(...) 就是「把命令的输出当成字符串塞进另一个命令」。
凡是「先查出来、再写进去」的流程，都应该用命令替换连成一条。
写死的值只配放进配置，不配放进运行状态。

今日收获

1. uniq 只认「相邻」，不认「相同」。
它没有全局哈希表，只跟上一行比。
所以 sort 不是优化项，是前提条件。统计三件套 sort | uniq -c | sort -rn，
两个 sort 各管一件事，少一个都不行。

2. 「怎么写都对」要怀疑数据，不要怀疑自己。
我的练习数据按 IP 分组写入，让漏掉 sort 的错误解法拿到了满分。
错误的答案在假数据上蒙混过关，在真实数据上原形毕露。
出题的人必须保证数据是乱的，否则考的是运气，不是能力。

3. 怀疑某个操作多余时，把顺序打乱再跑一遍。
shuf 一秒钟就能把假象变成事实。
这条方法不限于日志 —— 任何「加了没用」的错误认知，都可以用打乱输入的方式证伪。
