【运维实战】SSH 连不上新机器，我扒开 2.5GB 虚拟磁盘才找到真凶

发表于2026-10-23|更新于2026-10-24|云原生运维
|总字数:3.1k|阅读时长:11分钟|浏览量:

客户端发了公钥，服务端说不认 —— 那到底是谁的问题？

昨晚我给自己加了一台 Rocky 9.8 节点。今早连上去：

第一反应：老朋友了，authorized_keys 权限八成又不对。

于是我把这套排查流程又走了一遍 —— 目录权限、属主、sshd_config、StrictModes、
SELinux 上下文、公钥指纹对不对……

全对。 权限 600，属主 root，公钥内容一字不差，服务 active (running)。

但就是连不上。

那天晚上我盯着这台机器到十一点半，最后是把它那块 2.5GB 的虚拟磁盘扒开当证据扫了一遍，
才真正看到问题在哪。

一、能排除的都排除了，剩下的就很可疑

先说清楚哪些路是死路，免得你也往里钻。

死路一：网络

22 端口通，Banner 能读到。这里有个很好用的判据：能读到 SSH Banner，说明服务本身是健康的。
Banner 读不到 → 是服务没起来或网络不通；Banner 读得到但认证失败 → 是认证的问题。
这一刀下去，直接砍掉一半排查方向。

死路二：连错机器

万一这个 IP 上跑的是别的系统呢？把主机密钥指纹和预期值比一下：

一致。就是它。

死路三：客户端没把公钥发出去

这个最容易被忽略，因为报错信息里看不出区别。-v 一下就清楚了：

公钥确实提供了（Offering public key）。所以不是客户端的锅。

死路四：服务端配置拦住了

从客户端能拿到的信息有限，但服务端磁盘上的配置是可以查的（怎么查，后面第三节讲）：

放行的。root 登录许可有，密钥路径是标准的。

四条路全走完，stat 说没问题，sshd_config 说没问题，网络说没问题，客户端说没问题。

二、真正的破局点：别猜了，去看磁盘

走到这一步，继续在配置层面打转是没有意义的 —— 我需要的不是「配置是什么」，
而是「那个文件到底在不在」。

而这台机器是我自己用 VMware 建的，磁盘文件就在宿主机上：

vmdk 就是磁盘本体。 它是「稀疏 extent 的拼接文件」，里面装的是 ext4 / LVM 的原始字节。
既然如此 —— 我要的公钥，是不是就躺在这些字节里？

写个脚本扫一下：

输出：

公钥在源机上有，在新机器上一个字节都没有。

那一刻事情就清楚了。我一直以为新机器是源机的克隆，但克隆会把整个磁盘连同 authorized_keys 一起复制过去。
公钥不在，说明它压根不是克隆出来的 —— 它是一台全新安装的机器，
/root/.ssh/authorized_keys 从第一天起就是空的。

三、怎么把结论钉死：三条交叉验证

单看「公钥不在」还是有别的解释 —— 比如扫错了文件、扫漏了块。
所以我做了三层交叉验证，三层都指向同一个结论才算数。

第一层：磁盘几何

柱面数完全不同，extent 数量也是 16 个 vs 6 个。克隆必然完全一致，不一致就不是克隆。

第二层：挂载介质

虚拟机里还挂着安装 ISO。 克隆出来的机器不会自带安装介质 —— 这是新装的直接证据。

第三层：来宾机自己的启动参数（最有说服力）

这一层需要读来宾机日志。日志也在磁盘里，扫行格式就行：

扫出来的关键两行：

两条 kernel cmdline 一对比，真相自明：

cmdline 含义
inst.stage2=hd:LABEL=Rocky-9-8-x86_64-dvd 从 ISO 安装器引导 —— Anaconda 在跑
root=/dev/mapper/rlm_192-root 从 LVM 逻辑卷引导 —— 装完了，重启进了真系统

这台机器走过一次完整的全新安装流程，然后重启进了自己。 全新安装 = authorized_keys 是空的。

四、来宾机日志里那句 [preauth]

同一个离线扫描还捞出了别的东西。来宾机自己的 /var/log/secure：

四条信息，每条都有用：

① 服务健康 —— sshd[876]: Server listening on 0.0.0.0 port 22，时间点就在安装完成那一刻。

② 有人从控制台登录过 —— check pass; user unknown → FAILED LOGIN 1 FROM tty1 FOR sjl，
紧接着 ROOT LOGIN ON tty1。安装的时候用了一个不存在的用户名，失败后换 root 成功了。
这说明 root 密码是设过的 —— 也就是说，进得去。

③ 最后一段 [preauth] 是今天我自己的尝试，服务端在认证阶段之前就断了连接。

④ [preauth] 这个词值得单独说。

它精确区分了两种情况：

日志 含义
Connection closed by ... [preauth] 连接在认证开始前就断了 —— 公钥还没开始比对，会话从未建立
Accepted publickey / Failed publickey 认证完成了，服务端明确给了结论

配合客户端的 Offering public key: ... explicit，就能确定地断言：
客户端发了、服务端没接受，而不是「客户端根本没发」。

一个词，省掉一整轮猜测。

五、那到底怎么修？

根因清楚了，修复反而简单 —— 把公钥送进去就行。

问题在于：唯一的自动化入口（SSH 公钥）正是坏的那一环。
ssh-copy-id 自己也要先通过 SSH 认证才能干活 —— 用坏的东西修坏的东西。

所以只能走另一条路：VMware 控制台。

然后宿主机上验证：

顺序不能乱：先写内容，再改权限，最后 restorecon。
Rocky 9 默认开 SELinux，authorized_keys 的安全上下文不对，sshd 照样拒绝 —— 这个坑我之前踩过。

六、复盘：这次排查的方法论

1. 排障顺序比排障内容更重要

我今天在权限上耗掉的每一分钟都是浪费 —— 因为前提就不成立：
「公钥在服务端」这个前提没验证过，就直接进了权限分支。

正确的顺序应该是：

④ 是分水岭。 前三步都是几秒钟的事，但跳到 ⑤ 之前不确认 ④，
就可能在「权限完全正常」的死胡同里待到天亮。

2. 「主机密钥不同」证明不了「不是克隆」

我一开始就是这么判的：新旧机器 ED25519 指纹不一样，所以肯定不是克隆。

这个推理是错的。 全新安装同样会生成新的主机密钥 —— 指纹不同恰恰是两种情况共有的特征，
它区分不了任何事。

能区分的是「正相关证据」：磁盘几何、挂载介质、内核启动参数、文件内容。
指纹相同 → 一定是克隆；指纹不同 → 什么都说明不了。

3. 虚拟磁盘是不需要登录的取证介质

这是今天最有价值的收获。vmdk 里就是文件系统的原始字节，所以：

你想知道 扫什么
某个文件在不在 它的内容特征（公钥 base64 这种唯一性极高的串）
来宾机发生了什么 行格式（带时间戳的日志行正则）
系统是怎么启动的 kernel cmdline
装了什么版本 版本字符串

限制也要说清楚：只能证明「内容在磁盘上」，不能证明「当前生效」；
扫出来的是历史日志，必须靠时间戳对齐判断是哪个时段的事。

4. 「服务起来了」不等于「系统能用了」

这台机器的安装流程走完了 —— ISO 引导、Anaconda、重启、从 LVM 引导、sshd 起来，
一步不缺。但它：

  • 公钥没写进去 → SSH 连不上
  • 镜像站返回 503 → dnf install 全部不可用

它躺在「系统起来了」和「系统能用」之间。部署完成的判据不是「服务在监听」，
而是「服务能对外提供预期功能」。

5. 「今天没对话」不等于「今天没事做」

这条我写进自己的记录里已经第三年了。今天没有一条聊天记录，
但机器不会说谎 —— 我去读了进程、读了日志、读了 ARP 表、读了 2.5GB 的磁盘，
读出来的是一台昨晚刚装完、今早被认证卡住的新机器。

自动化跑得再勤也变不出内存，但读机器的真实状态随时能推翻旧结论 ——
包括推翻前一天的自己。

七、今日收获

  1. 「公钥在不在服务端」是分水岭，在它之前的排查（权限、SELinux、网络、配置）全是无效功。
  2. vmdk 可以当证据直接扫 —— 不登录来宾机，也能证明文件在不在、发生过什么、怎么启动的。
  3. 别拿「指纹不同」当「不是克隆」的证据 —— 那是共有特征，区分不了任何事。
    要用磁盘几何、挂载介质、kernel cmdline 这类正相关证据。
  4. 日志里的 [preauth] 值一个词的判断力 —— 它区分「认证没开始」和「认证被拒」。
  5. 服务在监听 ≠ 系统能用 —— 装完了、起来了、能用了，是三件事。
