【运维实战】跨云迁 Redis，我差点被「换个工具就能免提工单」骗了

发表于2026-10-27|更新于2026-10-27|云原生运维
|总字数:3.8k|阅读时长:12分钟|浏览量:

写方案的时候，我给客户画了一张三路线对比表，其中一条写着：

「用 RedisShake 自建通道，不依赖 SYNC/PSYNC，不需要提云厂商工单。」

这句话我是从天翼云官方文档里抄的。原话大意是：RedisShake 做在线全量迁移，不依赖 SYNC 和 PSYNC。

看起来挺美 —— 跨云迁 Redis 最麻烦的就是源端默认禁用 SYNC/PSYNC，得提工单等 3~5 个工作日。
现在告诉我换个工具就能绕过去，那整个排期风险点直接消失。

然后我去查了 RedisShake 自己的官方文档。

对于数据迁移场景，优先使用 sync_reader。一些云厂商没有提供 PSync 协议支持，可以选择 scan_reader。

两句话说的是同一件事，但结论完全相反。

天翼云文档没说错，RedisShake 文档也没没说错。错的是我 —— 我把一个工具的某一种模式的能力，
当成了这个工具的全部能力。

这篇写清楚三件事：这个坑到底坑在哪、正确的判断方法是什么、以及开工前 5 分钟能做完的自检清单。

一、先说清楚：为什么跨云迁 Redis 会被卡住

在讲我怎么错之前，得先讲清楚机制 —— 不然纠错就没有意义。

在线迁移的本质是「伪装成从库」

Redis 的主从复制流程是这样的：

数据迁移工具干的就是这件事 —— 它把自己伪装成源端 Redis 的一个从库。

所以你看这个链条上每一个环节被掐断会怎样：

被掐断的东西 后果
源端禁了 PSYNC 工具连全量都拿不到，因为第一步就 handshake 不上
源端主备倒换 复制流断裂，需要重连，中间会丢一段增量
存在大 Key 单次传输耗时长 → 复制缓冲区溢出 / 连接超时 → 表现为 connection reset by peer

第一行是致命的。 因为它不是「工具能力不够」，是协议层根本不让连。

这就是为什么几乎所有云厂商的 Redis 都默认禁用 SYNC / PSYNC —— 你要是能随便伪装成从库，
那这台实例就成了任何人的数据出口。

云厂商自己也是这么说的（华为云 DCS 文档）：

一般云厂商都是禁用了 SYNC 和 PSYNC 命令，如果要放通，需要联系云厂商运维人员放通命令。

⚠️ 这里有个特别容易踩的坑：华为云内部迁移（DCS → DCS，同账号同 Region）系统会自动放通，
但跨云迁移没有例外，必须人工提工单。

我最初以为「内部能自动放通，跨云应该也行」，直到翻到那句「没有例外」。

离线迁移的本质是「搬快照」

备份文件是某一时刻的静态 RDB，不含之后的任何写入。

  • 不需要 SYNC/PSYNC → 省掉了工单
  • 也不含增量 → 天然做不到增量（换来的是必须停机）

理解了这两条，后面所有的选型都是水到渠成的。

二、我错在哪：把「模式的能力」当成了「工具的能力」

RedisShake 有三个 reader 模式，这是官方文档里的表格：

模式 配置段 原理 需要 SYNC/PSYNC？ 一致性
sync_reader [sync_reader] 伪装从库，PSYNC + RDB 全量 + 增量流 需要 全量+增量
rdb_reader [rdb_reader] 读取本地 RDB 文件回放 不需要 静态快照
scan_reader [scan_reader] SCAN 遍历逐 key 搬运 不需要 弱

看这张表就清楚了：

  • 天翼云文档说的「不依赖 SYNC 和 PSYNC」，指的是 rdb_reader / scan_reader 这两种离线模式；
  • 而我想要的是在线增量迁移，对应的模式是 sync_reader；
  • sync_reader 的原理就是伪装从库，走的是同一条 PSync 协议。

所以：想不提工单又要增量 —— 做不到。
这是物理约束，不是工具问题。

我还漏看了一句更致命的

查 RedisShake 官方文档 others/checkpoint.md 的时候，还撞见这么一段：

RedisShake 4.x 不支持断点续传功能，也不支持感知集群拓扑变化。
网络中断、进程崩溃、服务器重启、集群扩缩容、主从切换等问题都可能导致同步终止，
中断后需要从头开始重新传输所有数据（Full Resync）。

对比一下：

RedisShake 云厂商 DTS
断点续传 ❌ 不支持，中断 = 从头来 ✅ 支持
拓扑感知（扩缩容/主备切换） ❌ 不支持 ✅ 支持
适合一次性迁移 ✅ ✅
适合长期同步 ❌ ✅

这比「要不要提工单」更关键。

工单是排期问题（等几天就解决了），断点续传是架构问题（几百万 key 的场景，网络抖一下就是几十分钟重传）。
官方对 RedisShake 的定位写得很清楚：适合一次性迁移，不适合长期同步。

用 RedisShake 迁移期间，必须保证链路稳定 + 有人盯着。

三、真正的解法：三条路线 + 一个决策树

理解了「协议层硬约束」之后，选型就变成了一张明牌。

路线 工具 需放通 SYNC/PSYNC 支持增量 业务中断 优先级
A 云厂商 DTS 控制台在线迁移 需要（提工单） 支持 秒级 首选
B RedisShake 自建通道 sync_reader 需要 / rdb_reader 不需要 sync_reader 支持 秒级 次选
C RDB 经对象存储中转 不需要 不支持 需停机 保底

决策树长这样：

三条路互为保底，任何一条被堵死都还有退路 —— 这才是交付方案该有的样子，
而不是「押注某一条路然后祈祷审批通过」。

但走哪条路，得先测写入量

有个问题必须先问清楚：你的数据涨得快吗？

这个答案直接决定路线，而且答案往往和直觉相反。

用 INFO commandstats 两次快照求差值就能算出来：

判定标准：

写入速率 结论
< 10 次/秒 备份离线迁移（对象存储中转）最省事
10 ~ 200 次/秒 优先在线迁移（DTS）
> 200 次/秒 必须走在线增量迁移，备份方案会丢数据

⭐ 反直觉的点：「数据增长很快」是反对备份路线的理由，不是支持它的理由

我一开始想当然地认为「数据涨得快 → 备份文件大 → 走备份迁移正好」。

错得离谱。

RDB 是某一时刻的静态快照，不含快照之后的任何新写入。而下载 → 上传 → 导入这三段是串行的：

数据越大，停机窗口越长，丢的数据越多。 增长快恰恰说明更不能用备份方案。

顺带说一个常见的方法论误区：有人会想「看历史备份文件的大小变化来估算增长速度」。

备份文件大小变化 ≠ 数据增长。 过期 key 被清理、value 被覆盖、压缩率波动，
都会影响文件大小。这个方法只能当参考，重要决策以实测写入速率为准。

四、开工前 5 分钟自检清单

把上面所有认知压缩成几条能直接抄的命令。开工前跑一遍，能省掉一整轮返工。

如果 PSYNC 不通：scan_reader 的真实代价

scan_reader 是免 PSYNC 的在线方案，但它不是免费的。官方文档标得很清楚：

  • 全量期间源端 CPU 压力大。官方实测数据：源端写 QPS 15 万时，源端 CPU 从 47% 涨到 91%；
  • DUMP 是 CPU 密集命令，会拖慢源端；
  • SCAN 期间可能漏掉新写入的 key，也可能搬进去已删除的 key；
  • count 调大提速，但源端压力线性上升。

要开 KSN 增量还得加条件：

⚠️ KSN 感知不到 FLUSHALL / FLUSHDB，迁移期间源端绝不能执行这俩命令。

五、云 Redis 是托管服务，你的「可见边界」只有两个入口

这条比技术细节更值得单独拎出来说，因为它决定了很多方案可行不可行。

云 Redis 和自建 Redis 的本质区别：

自建 Redis 云 Redis（托管服务）
进服务器 能 SSH，看 redis.conf、ps 登不进去，服务器在厂商机房
改配置 自己改 redis.conf 只能提工单
主备切换 自己管 控制台触发
备份 自己 BGSAVE 只能从控制台下载

只有两个入口：① 你的客户端（自己机器上装 redis-cli，用 IP + 密码连）② 厂商控制台（Web CLI / 监控面板 / 备份下载）。

几个由此推出的必然结论：

  • 无法 SSH 查源端是不是 Proxy 架构 → 必须实测 redis-cli PSYNC；
  • 无法改源端配置（比如 client-output-buffer-limit replica 太小导致断连）→ 只能提工单；
  • 备份只能从控制台下载 → 这就是「备份文件经对象存储中转」这条路线存在的原因。

顺便提醒：云厂商的 Proxy 架构是 PSYNC 的天然杀手。官方文档列了云厂商用 RedisShake 常见的三个原因：

  1. 引擎限制：自研 Redis-like 引擎不兼容 PSync；
  2. 架构限制：较多云厂商支持代理模式，即在用户与 Redis 服务之间增加 Proxy 组件。
    因为 Proxy 组件的存在，所以 PSync 协议无法支持；
  3. 安全限制：PSync 触发 fork 导致内存膨胀。

所以自测这一步不能省 —— 别等工单批下来才发现架构压根不支持。

六、复盘：这类坑的通用判断方法

1. 看到「不依赖 X」，先追问「哪个模式下不依赖」

今天我在同一个坑上踩了两次。

第一次：天翼云说「RedisShake 不依赖 SYNC/PSYNC」→ 我理解成「这个工具不需要」→ 错。

第二次：官方说「scan_reader 不依赖 PSync」→ 但紧接着就说了「需要源端开 KSN 且感知不到 FLUSHALL」。

通用动作：任何「不依赖」「支持」「兼容」的表述，都必须追问它在什么前提下成立。
厂商文档里这种话往往只描述了某个具体模式或某个版本。

2. 区分「工具能力」和「协议能力」

  • 工具能力：RedisShake 支持过滤 key、限速、改 value —— 这些是它独有的 ✅
  • 协议能力：PSYNC 是 Redis 复制协议的一部分 —— 谁实现都得走它 ❌

工具可以有很多种，协议只有一条。 遇到「换个工具行不行」的问题，
先判断这个卡点是在工具层还是协议层。协议层的，答案是「不行」。

3. 排障时先怀疑工具链，再怀疑数据

今天自测的时候还踩了个更隐蔽的坑：

校验脚本报「集合类型 key 全被误报目标端缺失」，现象看着像迁移漏数据。

真因是：Windows 下 redis-cli --scan 的输出带 CRLF，\r 混进了 key 名，
EXISTS 查的是一个根本不存在的 key。

如果当时第一反应是「迁移工具漏数据了」，接下来几小时全花在错误方向上。

教训：脚本报告的数据问题，先复现一次最小样本，确认是数据的问题还是脚本的问题。

4. 迁移完成的判定标准不是「任务状态 = 成功」

我给交付文档定的验收框架是四层：

层级 检查项 通过标准
L1 数据完整 Key 总数、类型分布 DBSIZE 一致，类型分布无异常偏移
L2 内容一致 抽样 Key 的值 + TTL 值全等，TTL 语义一致
L3 增量可追平 增量时延 写入到目标可见 ≤ 5s
L4 性能与业务 QPS / 延迟 / 业务功能 不低于源端基线 90%

「全量跑完」不是「可以切流」。 必须先过 L2 校验。

L2 这里有个细节值得单独说 —— TTL 判定要分两级：

  • TTL 语义不一致（一端永久 -1、另一端有 TTL）→ 判定失败，这是真问题；
  • TTL 数值偏差 → 仅告警，因为迁移过程中 TTL 必然流逝，要求完全相等不现实。

我第一版脚本没分这两级，结果数据完全一致也判失败 —— 这种误报会让人对整个校验脚本失去信任。

七、今日收获

  1. 「换个工具就能免提工单」是伪命题。 在线迁移的本质是主从复制，
    PSYNC 是协议层硬约束 —— 想不提工单又要增量，做不到。
    RedisShake 的 sync_reader 走的是同一条协议，只有 rdb_reader / scan_reader 才不依赖。
  2. 比「要不要提工单」更关键的判据是「断点续传」。
    RedisShake 4.x 不支持断点续传也不感知拓扑变化，中断即 Full Resync ——
    这是架构问题，比排期问题难解得多。
  3. 「数据增长快」是反对备份路线的理由。 RDB 是静态快照，下载→上传→导入三段串行，
    停机窗口 = 各段耗时之和。增长快恰恰说明更不能用备份方案。

一句话总结：跨云迁 Redis，先摸清写入速率（决定路线）和 PSYNC 能不能通（决定路线），
再动手。别信「换个工具就能绕过去」——
能绕过去的都是工具层的事，绕不过去的都是协议层的事。
