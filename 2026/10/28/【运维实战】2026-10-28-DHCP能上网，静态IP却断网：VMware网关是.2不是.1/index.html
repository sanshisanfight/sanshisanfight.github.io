【运维实战】DHCP 能上网，静态 IP 却断网：VMware 网关是 .2 不是 .1

发表于2026-10-28|更新于2026-10-28|云原生运维
|总字数:2.8k|阅读时长:10分钟|浏览量:

给虚拟机配好静态 IP 的那一刻，我是很满意的。

地址写对、掩码写对、网段也对。ping 网关一下——通的。

然后 sudo apt update，直接卡住。

能 ping 通网关，却完全上不了网。

这个组合最让人怀疑人生 —— 网关都通了，DNS 也解析出来了，网卡状态是 UP，路由表里有默认路由。

那一刻我的判断是「VMware 的 NAT 服务有问题」，差点去重装虚拟网络编辑器。

结果根因是：网关地址本身就填错了。而错的这个地址，还非常像是对的。

一、排查过程

第 1 步：确认不是网卡和路由的问题

先把「网络层配置对不对」这件事排除掉：

地址在、掩码对、默认路由在。看起来全对。

注意 proto dhcp 这个标记 —— 这台机器当时还在用 DHCP 续租。也就是说：

DHCP 下发的默认路由是 192.168.100.1，而且这个配置是能上网的。

这一条信息价值极大：同一个网关地址，DHCP 时代好使，我手写之后不好使。 那问题必然不在「网关地址」本身，而在我手写静态配置的其他部分 —— 或者，在我改动的过程中某个东西被覆盖了。

先记下这个矛盾，继续往下查。

第 2 步：分层测试，区分「二层通」和「三层通」

网络不通有两种完全不同的断法，混在一起查会绕死：

测试 命令 结果 说明了什么
二层（同一网段） ping 192.168.100.1 ✅ 通 网卡、驱动、ARP 正常
二层（宿主机外） ping 192.168.100.130 ❌ 不通 正常，隔离网段本就 ping 不到
三层（公网） ping 223.5.5.5 ❌ 不通 网关不做转发
三层（DNS 解析） getent hosts deb.debian.org ❌ 不通 连带失效，不是独立故障

关键结论：二层通，三层不通。

这意味着包发出去之后，在网关这个点上被丢掉了。网关不转发 —— 要么它不是网关，要么它被配置成不转发。

第 3 步：直接去问 VMware

到这一步已经排除了 Linux 侧（地址、掩码、路由表都没问题），那么答案在宿主机上。

VMware 的 NAT 配置文件在宿主机的固定位置：

打开它，看 [host] 段：

两个地址，一行注释，答案就在这里。

而我静态 IP 里写的网关是 —— 192.168.100.1。

也就是 hostIp，宿主机自己那张网卡的地址。

第 4 步：交叉验证

不放心，又用两个独立角度确认了一遍：

两条独立证据完全对上：DHCP 时代下发的网关是 .2，而 .1 是宿主机网卡。

我手写静态配置时，把 .1 当成了网关。

二、根因：为什么「能 ping 通」却「上不了网」

这是整件事最值得讲清楚的部分。能 ping 通网关，和网关能转发你的流量，是两件完全不同的事。

虚拟化网络里，.1 和 .2 分属两个不同角色

地址 角色 能不能当网关
192.168.100.1 宿主机在 VMnet8 上的网卡地址 ❌ 不能
192.168.100.2 VMware NAT 虚拟设备（一台跑在宿主机上的虚拟路由器） ✅ 必须指这个

为什么指向 .1 会「能 ping 通」

因为 ping 的目标是 192.168.100.1，那个 IP 确实真实存在，而且就在同一网段上 —— 它就是宿主机的 VMnet8 网卡。VM 发 ARP 请求，宿主机回包，二层链路完全正常。

所以：

但当 VM 要访问 223.5.5.5 时：

  1. VM 查路由表 → 默认路由是 via 192.168.100.1 → 封装成「目标 223.5.5.5，下一跳 192.168.100.1」的帧，发给 .1；
  2. 宿主机网卡收到这个帧 —— 但它不是路由器。Windows 默认不在这张网卡上做 IP 转发（IP forwarding 是关闭的）；
  3. 帧被丢弃。三层没有转发，包出不去。

一句话：

「能 ping 通网关」只证明了二层链路正常。
三层转发有没有做，是完全另一回事 —— 而你的网关，必须是一台真的会转发的设备。

为什么 DHCP 时代一切正常

因为 DHCP 下发的网关本来就是 .2：

从 DHCP 时代起，这个地址就一直在生效。apt install、yum install、pip install 全都正常 —— 因为从来没人需要手写这个地址。

直到我把静态 IP 写成了 .1，问题才第一次暴露。

换句话说：这个坑不是「配静态 IP 触发的」，是「手写网关触发的」。
DHCP 帮你挡了六天。

顺带一个更隐蔽的问题：DNS 不跟着变

改完网关、路由表对了、netplan apply 也执行了，但域名依然解析不了：

因为 resolv.conf 指向的是 127.0.0.53 —— systemd-resolved 的本地存根。真正的上游 DNS 是 systemd-resolved 缓存/管理的，netplan apply 只改路由，不一定触发它刷新。

（改完网关后这里还显示旧值，或者干脆是空的。）

补一条重启即可：

之后 resolvectl status 才正确显示上游 DNS。

正确的 netplan 静态配置

三个必须一起做的动作

1 via 指向 .2 外网不通（本次的根因）
2 chmod 600 配置文件 netplan apply 报 Permissions are too open
3 restart systemd-resolved IP 能 ping 通，域名解析不了

验证（三层都要测，不能只测一层）

三层全绿，才算「能上网」。

顺手给宿主机也加一条保险

确认宿主机确实知道自己该转发（Windows 宿主机）：

VMware 的 NAT 设备是独立于宿主机 IP 转发机制的（它自己就是个虚拟路由器），所以宿主机 Forwarding 显示 Disabled 是正常的，不用去开。别在这上面浪费时间。

四、复盘与延伸

通用判断方法：「能 ping 通网关」有三层含义，别混

测出来通的是 只能证明 不能证明
网关（.1 或 .2） 二层链路通、ARP 正常、对端设备活着 三层转发正常、外网通
公网 IP 三层转发正常 DNS 正常
域名 DNS 解析正常 应用层（TLS/端口/服务）正常

判断「能不能上网」只有一个判据：ping 一个公网 IP。
DNS 和应用层是另外两件事，别混进「上不上网」这个判断里。

怎么提前知道自己该填哪个地址

别猜，去问 VMware 自己的配置文件：

Windows 宿主机：

看 [host] 段，ip 那一行才是网关，hostIp 那一行是宿主机自己。

这类坑的通用形态：「看起来合理的默认值」

.1 是绝大多数网络的直觉默认值 —— 大部分家用路由器的网关就是 .x.1。正因为它太合理了，写错的时候没有任何报错。

netplan 不会校验「这个 IP 到底是不是网关」，它只管「把路由项写进去」。配置的合法性 ≠ 配置的正确性。

所以静态 IP 的验收标准必须包含「外网通不通」，而不是「配置文件对不对」。

一个反直觉的推论

我这次花了几小时，是因为 DHCP 时代把问题完美地掩盖住了。

凡是被自动化流程悄悄替你做对了的事情，一旦你需要手动接管，它就会立刻变成一个坑。
而且是一个「以前怎么用都好好的」型坑 —— 这种坑最难查，因为你的经验会一直告诉你「这条路没问题」。

所以每次从 DHCP 切到静态 IP，都应该把全部四个验证（网关 / 公网 IP / DNS / TCP）重新跑一遍，而不是凭「以前 DHCP 下能上网」的记忆放过。

五、今日收获

  1. 「能 ping 通网关」不等于「能上网」。 网关 ping 通只证明二层链路正常；判断外网通不通，只能 ping 公网 IP。 我这次栽的就是这条。
  2. VMware NAT 的网关是 .2，.1 是宿主机网卡。 宿主机网卡不转发，指向它必然三层不通。答案在 vmnetnat.conf 里，不要靠猜 —— .1 太像默认值了，写错时零报错。
  3. 静态 IP 的验收必须跑满四层（网关 / 公网 IP / DNS / TCP）。DHCP 时代的好用经验，在手动接管的那一刻全部失效。
