【运维实战】ping 得通却 curl 超时，我用 tcpdump 抓出了非对称路由

发表于2026-10-29|更新于2026-10-29|云原生运维
|总字数:3.1k|阅读时长:12分钟|浏览量:

宿主机 curl 得通，飞牛 curl 超时，ping 两边都通

我在做一件事：让一台 NAS（物理网段 192.168.200.x）上的 Prometheus，去采集三台
VMware 虚拟机（NAT 网段 192.168.100.x）的监控指标。

NAT 网段的机器已经装好了 exporter，从宿主机上 curl 完全正常：

然后我从 NAS 上 curl 同一个地址：

注意这里的区别：不是 Connection refused，是纯超时。

refused 意味着「包到了，端口没人听」；超时意味着「包压根没回来」。
这两种的排查方向完全不同。

更迷惑的是，ping 一切正常：

测试方向 结果
宿主机 → 虚拟机 ping 通，curl HTTP 200
虚拟机 → NAS ping 通
NAS → 虚拟机 ping 通，curl 纯超时

两个方向 ping 都通，curl 只有一个方向通 —— 这组合让我意识到这不是「谁没开机」，
也不是「防火墙拦了」，而是回包走错了路。

第一步：先排除掉所有「显而易见的」原因

这类问题的正确姿势不是猜，是逐层缩小范围。我在 NAS 上依次做了四组测试。

1.1 确认目标机器活着，且 exporter 在跑

从 NAS 上直连虚拟机本机：

exporter 活着，本机访问也正常。目标机器没问题。

1.2 确认 NAS 到虚拟机的路由是通的

下一跳是宿主机（192.168.200.115），路由存在。NAS 的路由表没问题。

1.3 确认宿主机这一跳在转发

这里踩了 Windows 上的第一个坑：IP 转发有两个独立开关。

接口级是 Enabled，但注册表里的 IPEnableRouter 还是 0。

Windows 的转发由这两个开关共同控制，只开接口级等于白干 —— 包到了宿主机就被直接丢掉。
顺带一提，Enable-NetIPForward 这个 cmdlet 在我的机器上根本不存在，
只能用 Set-NetIPInterface -Forwarding Enabled。

把注册表改成 1 之后，NAS 依然超时。所以转发开关只是前置条件，不是根因。

1.4 用对照法精确定位卡在哪一跳

这里我用一个很省事的判断法 —— 从两端各测一次，看断点落在哪：

测试 结果 说明
宿主机 → 虚拟机 通 虚拟机和宿主机之间没问题
NAS → 宿主机（192.168.100.1） 通 NAS 路由正确，包到了宿主机
NAS → 虚拟机 不通 卡在宿主机转发之后的某一跳

包已经到宿主机了，但宿主机把它交给虚拟机之后，回不来。

到这里基本可以确定：问题在回程路径上，不在去程路径上。

第二步：抓包，看 SYN-ACK 有没有回来

光靠推断不算数，抓包见真章。NAS 上没有 tcpdump，先装：

然后一边抓一边发请求：

同时另开一个终端：

抓包输出（修复前）：

只有 SYN，一个 SYN-ACK 都没有。

而且重传的 SYN 里，源地址变成了 192.168.100.133 —— 这就是关键线索。
说明虚拟机收到了这个 SYN（它回了一个 SYN-ACK，只是这个 SYN-ACK 在路上被丢了），
但回包在半路上被改写了。

去程正常，回程被改写。 根因就在这。

根因：回包绕了 VMware NAT，被改写源地址，然后卡在 conntrack 上

拆开看是两跳叠加。

第一跳：虚拟机的回包走了默认网关

虚拟机上：

192.168.100.2 是 VMware 的 NAT 虚拟设备（注意不是 .1 —— .1 是宿主机的
VMnet8 网卡，它不转发流量，这本身是另一个坑）。

虚拟机收到来自 192.168.200.98 的 SYN，要回复。但它的路由表里没有 192.168.200.0/24
的条目，所以只能走默认网关 → 交给 VMware NAT 设备。

VMware NAT 设备做的第一件事是 SNAT / MASQUERADE：把源地址从
192.168.100.133 改写成宿主机的 IP。抓包里那个 192.168.100.133 的源地址，
正是 NAT 设备的手笔。

第二跳：宿主机收到「源 IP 是自己」的包，conntrack 对不上，直接丢弃

包回到宿主机时长这样：

而宿主机上记录的原始连接是：

TCP 是有状态的。 宿主机靠 conntrack 表记着「我发出去一个包长什么样，回来的包必须
严格对应」才能续上这个连接。现在回包被改写成「源 IP = 我自己」，conntrack 一比对
对不上号 → 判定为无效包 → 直接丢掉。

为什么 ping 却通？

ICMP 是无状态的，没有 conntrack，也没有序列号要匹配。它靠 echo request / echo reply
的 echo id 配对 —— 而 NAT 设备改写源地址时会同时维护自己的映射，echo id 照样对得上。
所以 ping 侥幸能通，但这完全不能证明 TCP 通。

这就是那个指纹：ICMP 通但 TCP 不通 = 回程路径不对称（或经过了会做 NAT 的设备）。

一张图看清

虚拟机不知道 NAS 在 192.168.200.0/24，所以回包走了不该走的那条路。

解决方式：给虚拟机加一条回程路由

既然根因是「虚拟机不知道该往哪回包」，那就明确告诉它。

192.168.100.1 是宿主机的 VMnet8 地址（NAT 网段里宿主机那一侧），
把 192.168.200.0/24 指向它，回包就会绕过 VMware NAT，直接交回宿主机，
源地址保持 192.168.100.133 不变 —— conntrack 就能对上。

立即生效（先验证，别急着改配置）

加完立刻通。 我这边实测从超时直接变成 HTTP 200：

抓包也能看到完整的握手了：

SYN → SYN-ACK → ACK → 数据，完整配对。

持久化（这步不做，等于没修）

ip route add 是临时的，重启就没了。不写进配置文件的话，
症状会变成「昨天还好好的，今天又抓不到了」—— 这种问题最消耗人。

Ubuntu 上用 netplan 声明：

⚠️ 两个 netplan 的坑，顺带记一下：

  1. netplan generate ≠ netplan apply。 前者只生成
    /run/systemd/network/*.network，不会让 systemd-networkd 重载。
    我在这上面栽过一次：配置文件全对、生成文件也对，但运行态还挂着旧的 DHCP 地址，
    ip addr 里同时有静态 IP 和一个 secondary dynamic 的旧 IP，
    结果两台机器抢同一个 IP。排查网络问题永远查运行态
    （ip -4 -o addr show ens33），不能只看配置文件。
  2. 手写 netplan 和 cloud-init 生成的配置不能共存。 /etc/netplan/ 下同时有
    01-netcfg.yaml（手写静态）和 50-cloud-init.yaml（cloud-init 生成的 DHCP）时，
    netplan 会合并两者 → 静态和 DHCP 同时生效 → 同一张网卡挂两个 IP。
    根治是写 /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
    内容 network: {config: disabled}，再把 50-cloud-init.yaml 重命名掉。

复盘与延伸：三个能直接复用的判断方法

一、ping 通，只证明二层可达

我在这件事上浪费了时间的根源，就是反复用 ping 当判据。

ping 通 = 目标机回了 ICMP echo reply，仅此而已。它证明不了：

  • TCP 能不能建连
  • 转发有没有开
  • 回程路径对不对

判据要用 TCP 端口。 抓采集类故障，就用 curl http://<target>:<port>/metrics，
它同时验证了「网络通」「端口通」「服务在跑」三件事，比 ping 信息量高得多。

同理，refused 和 timeout 是两个完全不同的结论：
refused = 包到了但没人听；timeout = 包没回来。前者查服务，后者查网络。

二、遇到「两头都不通」，第一反应应该是查回程，不是查去程

去程路径好验证（发起方主动 curl 一下就行），回程路径容易被忽略。

抓包看到「只有 SYN，没有 SYN-ACK」时，就该问一句：回包走到哪儿去了？
这时在接收端（或中间的 NAT 设备上）抓一下源地址，
如果回包源地址不是它自己的地址，那就是被 NAT 改写了。

判据：抓包里回包源 IP ≠ 主机实际 IP ⇒ 路径上有 NAT 设备在改写 ⇒ 查回程路由。

三、跨网段的活儿，先把「路由表长什么样」画出来

不管 NAT 网段还是物理网段，每一台机器都要有一条明确的回程路由。
双向可达的前提是两边都写好了对方网段的下一跳，而不是「对方能访问我就行」。

我的最终配置（两台虚拟机一致）：

位置 配置
虚拟机 默认网关 → 192.168.100.2（VMware NAT 设备）
虚拟机 回程路由 → 192.168.200.0/24 via 192.168.100.1（宿主机）
NAS 静态路由 → 192.168.100.0/24 via 192.168.200.115（宿主机）
宿主机 接口级 Forwarding + 注册表 IPEnableRouter=1（两个都要）

宿主机的物理网段地址保持不动 —— 让 NAS 跨网段访问虚拟机，
靠的是 NAS 加一条静态路由指向宿主机，而不是改 NAS 的 IP。
改 NAS 的 IP 会让它脱离物理网段，反而丢掉外网。

今日收获

  1. 「ICMP 通但 TCP 不通」是一个可以复用的故障指纹，它几乎只指向一件事：
    回程路径经过了会做 NAT 的设备，或者回程路由缺失。
    下次再遇到，直接跳到抓包看回包源地址，别再从头 ping 一轮。

  2. 判据要选对。 ping 只能证明二层可达，curl <ip>:<port> 才能证明链路真的通了。
    排查监控采集、端口不通、跨网段访问这类问题时，
    判据本身选错，后面所有的排查都是在错误的方向上使劲。

  3. 临时修复不算修复。 ip route add 一行命令就搞定了，
    但不写进配置文件，下次重启照样复现 —— 而且会以「昨天还好好的」的形式出现，
    比一直坏着还难查。任何手工加的路由/规则，都要问一句：重启后还在吗？
