到这里为止，这个故事跟”换个源就好了”没什么区别。但我当时心里有个疙瘩没解开：

我到底是在修问题，还是在绕问题？

因为如果源是好的，为什么好的源会让构建失败？如果源是坏的，为什么 docker pull 同一个源又完全正常？

同一个镜像源，两种完全相反的结果。 这不像是”源坏”能解释的。

那天晚上我又登回 NAS 挖了三个小时。

排查过程

第一步：找到那句真正有用的报错

BuildKit 前端吐出来的错误只有一行半，而且没说是哪个源、哪个路径。真实信息在 daemon 日志里：

好，这行信息量很大，拆开看三件事：

  1. 失败动作是 HEAD，不是 GET —— 只取元数据（manifest），还没开始下载层。
  2. 阶段是 load metadata for docker.io/library/node:22-slim —— 注意 docker.io，这是 FROM node:22-slim 被标准化后的完整名字。
  3. 请求 URL 末尾有个 ?ns=docker.io。

第 3 点是全篇的关键。 这个参数我在 Docker 文档里从没印象，但它就明晃晃写在报错里。

第四步：决定性对照实验

到这一步，”源坏了”这个假设已经站不住了，但还差最后一块：它到底坏在哪儿？

三种访问方式，同一个源，同一台机器：

方式 请求长什么样 结果
A. docker pull <源>/<库> GET /v2/library/node/manifests/22-slim ✅ 200
B. BuildKit 解析 FROM HEAD /v2/library/node/manifests/22-slim?ns=docker.io ❌ 401

差别只有两个：HEAD vs GET，以及多出来的 ?ns=docker.io。

第五步：再挖一层 —— 两条路的 fallback 行为不一样

顺手做了个实验，故意拉一个不存在的标签：

注意报的是什么 —— 是下游 registry-1.docker.io 超时，不是 401。

这说明 classic puller 遇到第一个源失败时，会顺着 mirror 链继续往下试（fnnas → hub.docker.com → registry-1.docker.io）。

而 BuildKit 呢？它没往下走，直接 401 终止了。

我又把 daemon 日志翻了一遍，BuildKit 那次请求只有一条：

两条路径，两种 fallback 策略。 这解释了一个很常见的误判：

“我 docker pull 试过了啊，源是好的” —— 测的可能是另一条路。

根因

现在可以把整件事讲清楚了。

一、?ns= 是什么

它是 Docker Registry mirror 协议的一部分。

当镜像名是简写（node:22-slim）时，Docker 知道它其实指向 docker.io/library/node:22-slim。既然 docker.io 在国内基本没法直连，Docker 就会去找配置里的 mirror。

但 mirror 是个中转站，它背后也代理着一堆上游仓库。Docker 必须告诉它”我要的是哪个上游”—— 办法就是在 URL 后面加一个 namespace 提示：

厂商 NAS 的镜像代理（后端是 Harbor，www-authenticate 里的 service="harbor-registry" 直接点名了）就是靠 ns 参数决定把请求代理到哪个仓库。

二、401 的真正来源：scope 不匹配

回看那个 www-authenticate 头：

scope 就是一张授权票上写明的范围。 这张票写的是：

而 BuildKit 要的是：

同一个镜像路径 library/node/manifests/22-slim，两张完全不同的票，互不相通。

Docker Hub 上公用的镜像，走厂商代理时它要的 namespace 是 fnnas/library/*（厂商自己 App Store 那一套命名空间）；BuildKit 明确要求 docker.io，代理拿不出那张票 → 401。

所以根因是：镜像是同一个镜像，授权的命名空间不是同一个命名空间。

这也解释了为什么显式 docker pull docker.fnnas.com/library/node:22-slim 能成 —— 那条路径下 daemon 走的是 registry 客户端逻辑，请求形态和 scope 协商都跟 BuildKit 的 mirror 路径不一样。

三、为什么 BuildKit 不换下一个源

因为 BuildKit 的 load metadata 阶段和 classic puller 是两套独立实现，前者不做 mirror 链 fallback。

classic puller：images/create → 依次试每个 mirror → 失败继续下一个 → 全部失败才报错。
BuildKit：LLBBridge/Solve → 试第一个 mirror → 401 直接终止。

（这条不是猜的，是从 daemon 日志 + 上面那个”故意拉不存在标签”的对照实验里读出来的。）

四、一句话总结

Docker 镜像源”能不能用”这件事，取决于你用哪条路径去访问它。

docker pull 通 ≠ docker build 通。
curl /v2/ 通 ≠ docker build 通。

测源必须用你真正要走的那条路去测。

复盘与延伸

一个通用的 401 判读流程

不管是什么 registry，遇到 401 先跑这三条：

「同一个东西表现不同」的通用排查思路

今天这个坑的通用形态是：

A 路径能通，B 路径不通 —— 但 A 和 B 看起来是同一个东西。

这类问题的排查套路是固定的：

  1. 把两条路径的实际请求抓出来对比（不是猜，是看日志/看真实请求）
  2. 找出唯一的那个差异参数（今天是 ?ns=）
  3. 追这个参数的语义（它代表”要代理哪个命名空间”）
  4. 看鉴权上下文里的 scope 覆盖了哪些命名空间

第 3 步是分水岭。很多排查卡住不是因为证据不够，是因为拿到证据之后没有去查那个”看起来不重要”的参数是什么意思。 ?ns= 就那么一串小字，我要是只把它当成 URL 的一部分抄进工单，这事就永远结不了。

另一个值得记的点

我这次的”修法”是绕过（换源 + 打标签），不是修复（改 mirror 配置 / 换成正确的命名空间）。

绕过能让你今天把活干完，修复能让下一个人不用再踩。交付节奏允许你先绕，但别把绕过当修复忘了。 所以治本方案我也写在了上面，并且 daemon.json 那个改法是经过 docker info 验证过生效路径的。

关于厂商 NAS 的镜像代理

顺带一个观察：厂商 NAS 自带的镜像代理，服务的是它自己 App Store 那套命名空间，不是 Docker Hub 的公网镜像。

这不一定是设计缺陷 —— 它本来就不是给”拉公网镜像”用的。但它被写进了 registry-mirrors 这个全局默认位置，就会让所有 docker build 默认走它，然后集体 401。用厂商设备做容器平台时，第一件事就是把 registry-mirrors 换成自己验证过的通用加速器。

今日收获

1. 测源必须用你真正要走的那条路。
docker pull 通、curl /v2/ 通，都不代表 docker build 能过。今天如果我只是”换个源继续干活”，这个坑会原封不动留给下一个人。

2. 401 只是一把钥匙孔，得看它旁边写着什么。
www-authenticate 里的 scope= 才是真正的答案。同一个镜像路径，scope 差一点就是 401。看到 401，第一件事是找 scope，不是找密码。

3. 排障实验必须自带回滚路径。
我为了复现执行了 docker rmi，删的是正在被生产容器依赖的标签。动手前先确认备用镜像在不在手里，动手后立刻用业务健康检查确认没搞坏东西 —— 这不是洁癖，这是让自己还敢做实验的前提。
