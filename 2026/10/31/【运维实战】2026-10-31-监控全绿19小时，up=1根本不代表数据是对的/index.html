【运维实战】监控显示全绿，数据却串了19小时：up=1 根本不代表数据是对的

发表于2026-10-31|更新于2026-10-31|云原生运维
|总字数:3k|阅读时长:11分钟|浏览量:

监控里那条曲线是绿的。up=1，连续 35 个小时，一秒没断。

但我后来发现，有将近 19 个小时，Prometheus 采集回来的根本不是同一台机器的数据。

两台机器抢同一个 IP，一台关机的瞬间另一台悄悄顶了上来。Prometheus 依然尽职尽责地每 15 秒去敲一次门，对方依然乖乖回一个 HTTP 200 —— 于是 up 恒等于 1，监控全程零告警。

这不是配置写错了。这是从 Prometheus 默认配置开始就存在的结构性盲区：它测的是「端点通不通」，不是「端点后面是谁」。

一、先说清楚：为什么 up=1 骗了我

先摆现象。我的靶场里有三台被监控的机器，其中两台因为 IP 配置没落地，短暂持有过同一个 IP。

结果：up=1，从 10-29 09:00 一直到 10-30 20:10，205 个采样点，全是 1，一个 0 都没有。

监控视角里这台机器一直健康在线。完美。

然后我去查这条序列背后到底是谁在应答：

返回两个值：

同一个 IP 标签，前后被两台不同的机器应答过。

二、定位切换的那一刻

知道有漂移还不够，得知道什么时候换的。这里有个坑：我第一次用 step=600（10 分钟）去扫，边界糊得看不清。

改成逐分钟：

把两个 nodename 系列的采样点按时间排序输出：

⚠️ 「连续」是采样粒度的函数，不是事实。 10 分钟一采，你看到的「连续 up=1」可能只是把两段混在一起。要证明边界，必须把采样粒度降到和事件量级匹配。

三、根因：IP 冲突 + 采集器级别的身份缺失

分两层看。

表层：为什么会换人？

那台机器同时持有两个 IP —— 一个是 netplan 配的静态地址，另一个是 DHCP 租约残留。离线扫它的虚拟磁盘，能直接抓到这一行：

同一个网卡，两个 IP，共存。

于是：持有 .134 的那台关机 → DHCP 租约残留的那台发现「这个 IP 没人抢了」→ 它的 node_exporter 照常在 :9100 应答 → Prometheus 敲 .134:9100，有人回 → up=1。

深层：为什么监控没告警？

因为 node_exporter 暴露的指标里，身份信息是有，但默认没人拿它做判据。

node_uname_info 带 nodename 标签，node_network_info 带 MAC 标签。这些信息 Prometheus 全都采到了，躺在时序库里没人看。默认的告警思路是「端点不通就报」——而这里端点一直通。

这才是真正的盲区：不是没数据，是有数据但没人在用。

四、第二个判据：MAC 地址

只靠 nodename 一个判据，我不太放心 —— 万一它也是巧合呢？于是换了个完全独立的维度交叉验证：

两个不同的 MAC。 和 nodename 的结论完全吻合，且这两条证据链互不依赖 —— 一个来自内核 hostname，一个来自网卡硬件。

更直接的证据是：那条新 MAC 00:0c:29:xx:xx:xx 同时出现在 .133 和 .134 两个 instance 上：

同一块网卡，同一个 MAC，两个 IP 标签。这是「一台机器顶了两个身份」的直接物证。

顺带踩的坑：boot_time 在克隆场景下完全没用

我一开始也想用 node_boot_time_seconds 做判据，结果两台机器的值一模一样：

因为这两台是同一批克隆出来的，镜像里继承的启动时间戳一样。

克隆这件事有个规律，选判据前必须先想清楚：

属性 克隆后会不会变 能不能当身份判据
nodename（内核 hostname） ✅ 会变（克隆工具要求唯一化） ✅ 能
网卡 MAC ✅ 会变（虚拟化软件重新生成） ✅ 能
boot_time ❌ 不变（镜像继承） ❌ 不能
machine 标签 恒为 x86_64（CPU 架构） ❌ 不能

五、写出真正能触发的告警规则

判据选好了，规则就好写了。核心就一句：同一个 instance，窗口内出现过几个不同的 nodename。

这段嵌套 count 的两层语义值得拆开看：

  • 内层 count by (instance, nodename) (count_over_time(node_uname_info[7d]))
    → 按「instance + 身份」分组，统计每个身份在窗口内出现了多少个采样点
  • 外层 count by (instance) (...)
    → 按 instance 分组，数一数底下有几个不同的身份
  • > 1 → 漂移

[7d] 窗口意味着漂移发生后最长 7 天内都能被查出来。代价是修好之后还会继续告警 7 天（历史数据还在窗口里）—— 这是个需要提前接受的特性，不是 bug。

这才是我觉得最值钱的部分 —— 上线不等于生效，每条规则都得单独验。

问题一：第三条规则永远不会触发

我原本还写了一条「硬件指纹不一致」的规则：

永远返回 1，条件恒不成立。

根因是我把 machine 这个标签想当然了。 它的值是 CPU 架构，不是机器身份：

NAS 是 AMD x86_64、node-1 是 Ubuntu x86_64、node-2 也是 x86_64 —— 全体同值。

我试过找真正的硬件指纹 machine_id / boot_id，但 node_exporter v1.12.1 的 node_uname_info 根本不暴露这两个标签（对着原始 /metrics grep 计数为 0）。

所以这条规则只能作废，换成 MAC 判据 —— 也就是上面那条 TargetMacDrift。

⭐ 每条告警规则上线后都要单独验证一次它的表达式在真实数据上会返回什么。
「规则加载成功」只证明 YAML 语法对，不证明它能触发。 我今天有 4 条规则，2 条真能响、1 条永远不响、1 条是纯噪声。

问题二：有一条在响的告警是纯噪声

TargetDown 报「靶场节点失联超过 5 分钟」，三个 target 全在报。但我去查 VM 状态：

三台机器本来就没开机。 「本来就该关着」被当成了「挂了」。

更微妙的一个：另一个 target 我查了它的历史 up：

它从来没被成功采集过一次 —— 因为压根没装 node_exporter。 但在 up 指标上，「没装采集器」和「装了但挂了」长得一模一样。

⭐ 光看 up 无法区分「刚挂」和「一直没上线」。
必须回查「这个 target 历史上有没有成功过」，才能判断它是哪种情况。

最后一个洞：告警响了，但没人会收到

我这次是直接 curl /api/v1/alerts 才看到告警的。为什么？因为 NAS 上根本没装 Alertmanager：

Prometheus 里有规则 ≠ 有人收到通知。Alertmanager 才是「分组 + 抑制 + 路由 + 通知」的那一段。 没有它，告警只躺在 API 里，得手动 curl 才看得见 —— 等于没做告警。

七、复盘：这类问题怎么提前发现

三条可迁移的判断方法：

① 监控要显式回答「这个 IP 后面是谁」

默认配置只回答「这个 IP 通不通」。只要环境里存在 IP 漂移的可能（DHCP、克隆、多网卡、容器网络），就必须加身份维度。 好消息是 node_exporter 已经把身份给你采集好了，你只要用。

② 判据要选「克隆会改」的字段

nodename 和 MAC 会改，boot_time 不会改，machine 压根不是身份字段。先问「这字段在故障场景下会变吗」，再写表达式。

③ 告警规则要逐条验证「能不能触发」

规则加载成功 ≠ 规则有效 ≠ 规则不吵。三件事分开验：

  • 能不能触发 → 拿真实数据跑表达式，看返回什么
  • 触发得对不对 → 跟根因对时间线，验 activeAt
  • 会不会太吵 → 看它报的 target 是不是本来就该 down

八、今日收获

  1. up=1 只证明「端点活着」，不证明「数据是对的」。 19 小时的污染里 up 一次都没断过 —— 你的监控会给你一个漂亮的全绿。必须额外加身份判据。
  2. 克隆会改 hostname 和 MAC，不会改 boot_time。 选身份判据前先确认这个字段在故障场景下会变。
  3. 告警规则要逐条验证能不能触发。 我今天 4 条规则，2 条真响、1 条永远不响、1 条纯噪声 —— 「加载成功」只证明 YAML 语法对。
  4. 告警分「发现」和「送达」两段。 没有 Alertmanager，告警就只在 API 里躺着。

本文所有 IP 均为脱敏后的示例值。真实环境中的现象、命令与结论均来自实际排障过程。
