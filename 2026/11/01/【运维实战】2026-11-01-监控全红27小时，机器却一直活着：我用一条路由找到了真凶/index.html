【运维实战】监控全红27小时，机器却一直活着：我用一条路由找到了真凶

发表于2026-11-01|更新于2026-11-01|云原生运维
|总字数:2.9k|阅读时长:10分钟|浏览量:

监控面板上，三台机器整整红了 27 小时。

我 SSH 上去看 —— 机器活着，node_exporter 明明是 active，9100 端口明明在监听。

监控说它死了，机器说它活着。 谁在撒谎？

一、先确认「机器确实活着」

这一步不能跳。很多人一看到 up=0 就去重启机器、查服务、重装 agent —— 方向从第一步就错了。

服务活着，端口在监听。机器没问题 —— 那问题就不在目标机上，在「采集器怎么走过去」这条路上。

同样的结论也可以从 Prometheus 自己那边拿：

context deadline exceeded —— 超时，不是拒绝。

这个细节值得停一下：连接被拒绝（connection refused）说明「到了那台机器，但端口没开」；超时说明包发出去石沉大海，路根本没通。两者的排查方向完全不同。

再看采集量：

12:20 那一刻断的。 精确到分钟，不是「最近不太好使」。

二、从「超时」推出「路断了」

超时只说明包没回来，没说在哪丢的。这时候要做的不是猜，是让链路上的每一段自己作证。

第 1 段：采集器 → 目标机

000 = 连接根本没建立起来，而且耗时打满 6 秒超时上限。机器没回包。

第 2 段：目标机 → 采集器（回程）

回程也不通。双向都不通，说明问题在中间，不在某一端。

第 3 段（胜负手）：包实际往哪走？

到这一步大部分人开始查防火墙了。但防火墙是第四层的，前面还有第三层 —— 路由。

这一步是本次定位的胜负手。它不告诉你「路由表里有什么」，它直接回答内核实际会怎么走这个包：

等一下。

这个网段该走的那条路由，指向的是默认网关（.200.1，路由器），不是它本来该走的那台宿主机的物理地址（.200.115）。

包被交给了路由器，路由器不认识 192.168.100.0/24 这个网段 —— 于是包就石沉大海了。超时，而不是拒绝，因为路由器通常不会主动回一个 ICMP 拒绝。

再确认一遍路由表：

路由表里没有这条网段的条目。 走默认网关是「查不到就丢给 default」的兜底行为，不是「本来就这么设计的」。

三、根因：手工加的路由，被网络管理器收走了

路由表里没有这条路由。那它是什么时候没的？

先看配置还在不在 —— 因为「配置」和「生效」是两回事：

配置里明明写着这条路由！ 文件 mtime 是 2026-10-28 23:56:36。

这就是最迷惑的地方：配置文件是对的，内核里却没有。

而且网络管理器自己也认这条路由：

那内核里为什么没有？因为当时真正生效的不是这条配置，是手工加的。

翻出几天前的操作记录（这行是我自己当时敲的）：

手工 ip route add —— 这条命令立刻生效，监控当场恢复。但它是运行时状态，不归 NetworkManager 管。

于是谜题解开了：手工路由能跑，但活不过一次网络管理器的重载。

决定性实验

猜测要验证，不能靠推理。做个对照实验：先手工加一条测试路由，再触发一次网络重载，看它会不会消失。

实验成立。 nmcli device reapply 会重置该设备的全部路由，只保留它自己 profile 里声明的那条。

再看重载之后内核里的实际形态：

proto static metric 100 —— 这是 NM 托管的形态（metric 100 正好对应 profile 里的 route-metric=100）。而手工加的那条是裸的，没有 proto 也没有 metric。

结论：这几天我一直靠手工路由撑着，而 NetworkManager 某次重载（比如 DHCP 续租触发的接口重配）把它连本带利收走了 —— 只留下它自己 profile 里声明的那条。可 profile 里那条虽然写着，当时却因为各种原因没被下发到内核。

于是：路由在配置里、命令也对、机器也活着，但包走错了门。 从 10-30 12:20 到今天 15:20，27 小时。

顺带一提，这跟 netplan generate ≠ netplan apply 是同一个病根的另一张脸：
「配置文件里写着」不等于「内核里生效着」。
只不过那次是 netplan 不重载，这次是手工路由被 NM 回收 —— 都是「你以为配好了，其实没生效」。

四、修复：让 NetworkManager 接管这条路由

两步：先把路修通，再把它交给能持久化的那一层。

验证连通性（这一步必须做，别假设好了）：

验证监控真的收回来了（等一个采集周期）：

图上的红线，在 15:14Z 那一刻变回了绿色。

顺便说一句：修复后我又逐一验证了三台机器 —— .133 和 .134 都是 http=200，但 .135 仍然是 http=000。
因为 .135 是真的没装 node_exporter（systemctl is-active 返回 inactive，9100 根本没监听）。
同一个 up=0，一台是误报，一台是真故障。 这两件事必须分开处理。

五、复盘：这类故障以后怎么一眼认出来

1. up=0 有两个完全不同的含义

up=0 的真相 判别方法 本次实例
目标真的挂了 目标机本地 systemctl is-active + ss -ltn .135（真没装 exporter）
采集侧到目标的路断了 采集器 curl 超时 + ip route get <目标> 看选路 .133 / .134（NAS 路由被回收）

「机器活着但监控说它死了」和「机器真死了」，在监控面板上长得一模一样。 光看图永远分不出来。

2. 对照判读法：让链路每一段自己作证

同一个现象（超时）至少有四个可能断点：目标服务 / 目标网络栈 / 中间路由 / 采集端路由。
不要顺着一条链路猜，要交叉验证：

测试 命令 结果说明
目标服务活着吗 目标机 systemctl is-active / ss -ltn 排除目标端
采集器能到吗 采集机 curl -m 6 <目标>:9100/metrics 看是超时还是拒绝
包往哪走 ip route get <目标> ⭐ 一眼看出走错网关
回程通吗 目标机 ping <采集器> 双向都断 = 问题在中间

3. ip route get 和 ip route show 是两回事

  • ip route show = 路由表清单（表里有什么）
  • ip route get <目标> = 内核的实际选路结果（包真的往哪走，含 metric 比较后的胜出条目）

排查「包到底往哪走」必须用 ip route get。本次就是它一眼看出「走了默认网关而不是该走的那台宿主机的物理地址」。

4. 凡是长期需要的配置，都要交给能持久化的那一层

手工命令是临时借来的，网络管理器重载时连本带利收走。

  • 手工 ip route add → 活不过一次 nmcli device reapply
  • netplan generate → 不等于 netplan apply
  • nmcli connection modify → 只改文件，不重载；改完要 nmcli device reapply 或 nmcli connection up

判据很简单：改完配置，去内核里看一眼实际生效的对象，别看配置文件。

5. 修好之后告警还在响，不等于没修好

这次身份漂移告警（TargetIdentityDrift / TargetMacDrift）在我修好路由之后依然在 firing。
因为告警表达式用的是 count_over_time(node_uname_info[7d]) —— 7 天窗口里还装着历史污染样本。
修复只改变「现在」，改变不了「过去 7 天」。

判据要用当前值（查 .134 现在的 nodename 已经是正确的那台），而不是「告警消了没有」。

6. 最后一条，也是最要命的一条

这套环境当时没有 Alertmanager。 3 条告警在 firing，告警只躺在 Prometheus 的 API 里，得手动 curl 才看得见。

所以这次 27 小时的静默断采，全程没有任何人收到通知 —— 我是 23:00 例行核验时才发现的。

没有通知渠道的告警，等于没有告警。
Prometheus 里有规则 ≠ 有人收到消息。Alertmanager 才是「分组 + 抑制 + 路由 + 通知」那一段。

今日收获

  1. up=0 不等于机器死了。 它只说明「从采集点到目标端点这条路不通」。判断之前，先让目标机自证活着，再用 ip route get 看包实际往哪走。
  2. 长期配置要交给能持久化的那一层。 手工 ip route add 活不过一次网络管理器重载；netplan generate 不等于 netplan apply。改完永远去内核里验证，别看配置文件。
  3. 静默故障只能靠例行核验发现。 没有 Alertmanager，27 小时的监控全红可以一直躺在 API 里没人知道 —— 先补通知渠道，再谈告警规则。

这次的排查链条我写成了可复用的判读表，存进了运维工具库。下一篇打算写考试平台那套东西：
为什么「让用户在网页里敲命令、后端执行」这个设计被我砍掉了 —— 因为它等于把靶场后门开放出去。
