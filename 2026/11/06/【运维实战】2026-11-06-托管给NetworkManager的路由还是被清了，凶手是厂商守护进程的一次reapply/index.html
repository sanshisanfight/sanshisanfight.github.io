【运维实战】托管给NetworkManager的路由还是被清了，凶手是厂商守护进程的一次reapply

发表于2026-11-06|更新于2026-11-06|云原生运维
|总字数:3.3k|阅读时长:12分钟|浏览量:

三天前我修过一次同样的问题。当时的结论是：静态路由不能手工 ip route add，得交给 NetworkManager 托管。

我以为这事到此为止了。

结果第二天晚上例行核验，同一条路由又不见了。

一、路由在配置里，也在内核表里，但它就是不生效

NAS 上要访问另一网段的靶场机器，路由是这么配的，一直好好的：

proto static metric 100 —— 这是典型的 NetworkManager 托管形态，不是手工加的临时路由。

但那天晚上：

走了默认网关。静态路由等于不存在。

最迷惑的地方在于：配置文件里明明还在。

配置正确，内核不认。同一个东西，两个状态源，而且是打架的。

三台靶场机器同时从 Prometheus 掉线，up=0。但机器明明开着、9100 端口明明在监听。

二、排查：先分清「配置层」还是「内核层」

这一步没什么技术含量，但跳过去就会绕远路。

排掉策略路由和多表：

主表、策略表、所有表都翻了一遍 —— 路由不是藏到别的表里，是真的没了。

排掉机器状态：

同一台 NAS，通宿主机，通不了靶场网段。问题定位在 NAS 的出向选路，不在机器、在采集器、在 Prometheus。

顺手记一条判读纪律：up=0 必须先分清是「机器没开机」还是「采集侧断了」。
我这次差点又当成机器挂了 —— 后来查 vmware.log 才发现三台 VM 确实全关机了，
但 NAS 到 9100 的探测同样不通，两个原因叠在一起，只看 Prometheus 的图永远猜不出来。

三、根因：谁动的手，日志里写得清清楚楚

既然东西「凭空消失」，那就该问「谁删的」。

NetworkManager 的 audit 日志把这件事记得比我还清楚：

四个信息一次性到齐：

字段 值 含义
op device-reapply 有人对网卡做了一次重载
args ipv6.routing-rules,ipv6.routes 只点了 IPv6 这两项
pid 1456 是谁干的
时间 11-04 20:38:06 精确到秒

查这个 PID 是谁：

network_service —— NAS 厂商（fnOS）的自研守护进程，路径 /usr/trim/bin/network_service。

根因就此明确：

厂商守护进程在 20:38 调用了一次 nmcli device reapply 的部分重载，
参数只包含 IPv6 的两个属性。
NetworkManager 只重载「参数里点名的配置族」，
没点名的那些 —— 包括这条 IPv4 静态路由 —— 被它认为「不归本次重载管」，顺手从内核路由表里清掉了。

为什么「部分」是关键词

device-reapply 有两种形态，效果完全相反：

同一个操作，只因参数集不同，结果相反。

三次失败的复现，和它们意外泄露的信息

我试着干净地复现一次「只带 IPv6 参数的部分 reapply 抹掉 IPv4 路由」，四连败：

但这四次失败，比四次成功更有价值。

  • unknown setting name → 告诉我外层 key 应该是设置名（ipv6），不是属性名（ipv4.routes）
  • can't set property of type 'a(ayuayu)' → 直接把期望的 D-Bus 类型签名打脸给我，省了翻源码
  • connection: setting not found → 指出参数集还差一个 connection 段

这就是我一直强调的那条：恒定失败的响应比成功的信息量大。
成功只告诉你「成了」，失败会告诉你「差在哪个字段、期望什么类型」。
排查时看到 4xx/5xx 别急着跳过 —— 把报错读成线索，而不是读成终点。

诚实边界：上面那个 connection 段我至今没补上，
所以「只带 IPv6 参数的部分 reapply 会抹掉 IPv4 静态路由」这个机制，
我是靠 audit 日志的实证 + 全量/部分重载的行为对照推出来的，不是靠一条干净复现命令证出来的。
根因链本身是实测成立的（谁、何时、带什么参数、造成什么后果，全部有日志），
但「构造出同样参数集并复现」这一步还没闭环。

四、修复：不是补一条路由，是让它能自己回来

先手工补上，让业务恢复：

但这只是把这一次的问题按下去。根因还在 —— 厂商守护进程随时可能再来一次部分重载。

所以真正的修复是自愈看门狗：定时检查实际选路，发现不对就自己修回来。

装进 cron，每 5 分钟一次：

再配个 logrotate，别让日志把盘撑爆：

判据为什么是 ip route get 而不是配置文件

这是整个修复里最关键的一行。

本次事故的原型就是：配置文件一直是对的，错的是内核。
用配置文件当判据，看门狗会永远报「一切正常」，然后路由一直是坏的。
判据必须取实际生效的那个状态。

主动打断验证：破坏比等待更能证明修复是真的

装完不能就宣布「修好了」。主动制造一次故障：

修之前是 100% 丢包，修之后 0%。而且这次是我自己打断的，不是等厂商守护进程什么时候心情好再来一次。

两天后复核，修复稳稳活着：

看门狗日志里只有当初故意打断的那两条，之后一直安静 —— 说明路由真的没再掉过。

五、复盘：我三天前的修复是错的

三天前我也遇到过一模一样的现象，静态路由被清空。那次的根因是「手工 ip route add 加的路由活不过一次 nmcli device reapply」，我的修复是：改用 NM profile 托管，让它变成 proto static metric 100。

我当时觉得这事解决了。

这次证明我错了。

三天前 这次
路由怎么来的 手工 ip route add NM profile 托管
谁抹的 我自己执行的 nmcli device reapply 厂商守护进程 network_service
重载参数 全量 只带 IPv6 的部分重载
我的结论 「托管给 NM 就安全了」 ❌ 托管不等于被保护

同一个根因，两次不同的暴露面。

我那次的修复之所以「看起来对」，是因为我修复的对象是路由的添加方式，
而真正的根因是路由会被别人的部分重载顺手清掉。
换句话说 —— 我修的是症状，不是病因。

⭐ 「托管」只回答「谁负责写」，不回答「谁会动它」。
把配置交给某个组件管理，不等于那个组件会保护它不被别人删。
托管解决的是「配置漂移」，不是「并发修改」。

还有一条：托管还给你一种虚假的安全感。
nmcli 显示一切正常，你会下意识地不再去查内核。
而这次的故障恰好就是「显示正常、实际不生效」。

六、通用判断方法

下次再遇到「东西不见了」，按这个顺序走：

1. 先分清是「配置层」还是「运行态层」丢了

三个都要看。只看到第一个就下结论，是这类故障最常见的翻车方式。

2. 排掉策略路由与多表

3. 问「谁动的手」

audit 日志的 op / args / pid / 时间戳四件套，通常直接给出答案。

4. 排掉「机器自己不行」

5. 修复后一定要主动打断验证

ip route del → 跑修复 → 看能不能自己回来。别用「装完了」代替「验证过了」。

6. 如果根因在别人家的守护进程里，加自愈而不是加告警

告警只告诉你出事了，自愈直接把它修好。
每 5 分钟一次的自愈，比一次事后排查便宜一百倍。

今日收获

一、「配置里有」和「生效了」是两个独立的事实，中间隔着一个内核。
netplan generate ≠ apply、profile 有 ≠ 内核表有、NM 托管 ≠ 不会被清 ——
这是同一个坑的三种形态。

二、排障第一步永远是「先定位到哪一层」，而不是「怎么修」。
配置层 / 运行态层 / 实际选路，三层各查一遍，方向就出来了。

三、恒定失败的响应比成功的信息量大。
unknown setting name 告诉我 key 该填什么，can't set property of type 'X' 直接把类型签名给我。
把报错读成线索，而不是读成终点。

四、修复要主动打断验证，而且判据要取「实际生效的那个状态」。
ip route get 而不是 nmcli con show —— 用错判据的看门狗，会在故障发生时报「一切正常」。
