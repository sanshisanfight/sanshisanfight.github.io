【运维实战】迁移校验脚本说"数据一致"，根因是CHECKSUM对不存在的表返回NULL

迁移做完，最后一步是校验两端数据一致。

我的脚本长这样：跑一遍 CHECKSUM TABLE，把两端的输出抓出来，逐行比对字符串。

跑完，两端完全一致，校验通过。

然后我去查了一下实际校验了哪些表——

一张都没校验到。

一、现象：绿色的报告，覆盖了零张表

先看真实环境。源库上有两张表，我做过一次停机导出，要把它迁到目标机：

数字是稳定的，每次跑都一样——因为 MySQL 把表里每一行算一次 CRC32 然后累加。任何一行、任何一个字节变了，这个数字就变。

（这组校验和来自我本地靶场里一套完全合成的测试数据——1000 条订单 + 50 个客户，字段与内容均为生成物，不是任何真实业务数据。真实环境里你跑出来的是另一组数字，但「两边必须相等」这条性质完全一样。）

迁移到目标机之后，我在目标机上跑同样的命令。假设目标机上的表名打错了一个字母：

等一下，如果表名打错了，这里应该报错才对。

那如果两端都打错了呢？

我的脚本逐行比对字符串：NULL == NULL → 一致 → 校验通过。

脚本没报错、退出码是 0、报告是绿的、结论是”数据一致”。

而真实情况是：这两张表从头到尾就没被校验过。

二、排查：四种写法，一次打全

我一开始怀疑是权限、字符集或者表结构的问题。于是把 CHECKSUM TABLE 的各种写法在源库上连打了四遍，逐条对比输出。

写法 A：不带默认库，直接给表名

报错了。 这是个语法层面的失败——命令本身合法，但没有指定当前在哪个库，MySQL 不知道 customers 指的是哪张表。

写法 B：先 USE，再给表名

✅ 正常。

写法 C：全限定名

✅ 正常，和写法 B 数值完全一致。

写法 D：换成一张不存在的表

这就是真凶。

注意发生了什么：

  • 没有 ERROR
  • 没有警告
  • 退出码 0
  • 输出里甚至有一行，看起来完全正常
  • 唯一的异常是 Checksum 那一列写着 NULL

三、根因：解析层的失败会报错，数据层的缺失只回 NULL

把 A 和 D 放在一起看，这两种失败的性质完全不同。

写法 A（没选库）失败在解析层。 命令送到 MySQL，MySQL 先要确定「表名相对哪个库解析」，这一步就卡住了——没有默认库可选，语法上根本走不下去，所以报 ERROR 1046。

写法 D（表不存在）失败在数据层。 语法完全合法、库也选对了、权限也够。MySQL 解析出「要校验 appdb.nosuchtable」，然后去打开这张表——发现没有这张表，于是没有数据可以算 checksum。它不会说”你要的表不存在”，它只是说”这张表算出来是 NULL”。

用一张表来理解这个区别：

失败类型 发生阶段 MySQL 的反应 你的脚本看到
没选默认库 解析层 语法走不通 ERROR 1046，报错
表不存在 数据层 表打开失败，无数据可算 Checksum = NULL，不报错
权限不足 授权层 拒绝访问 ERROR 1142，报错

⭐ 规律很干净：凡是「命令本身没法执行」的失败，MySQL 都会报错；凡是「命令能执行但目标不存在」的失败，MySQL 大概率只给你一个空值。

而我们的脚本只认「有没有输出行」和「字符串是否相等」——它无法区分「算出 NULL 的真实数据」和「根本没有这张表」。

NULL 到底意味着什么

CHECKSUM TABLE 的语义是「把表里每一行的 CRC32 累加」。表不存在 → 没有行 → 累加结果为空 → NULL。

也就是说，NULL 不是「校验失败」，是「没有东西可校验」。

四、解决：三层验收法

既然单靠 checksum 一层会漏表，就得加层。

第 0 层：先确认「校验器本身会不会失败」

这是最重要的一条，也是我今天最大的收获：

任何校验类命令，上线前必须先证明它「能失败」。

具体做法：故意传一个不存在的对象，看它是否报错。

  • 如果它报错了 → 说明这个校验器会告诉你「东西不存在」，可以放心用
  • 如果它回 NULL 不报错 → 那你的脚本必须把 NULL 显式判为失败

这条思路是通用的：「测某能力能不能用」必须用你真正要走的那条路径去测（10-30 踩过同样的坑，那次是 docker pull 通但 docker build 不通）。迁移校验器也一样——你不能因为它返回了数字就相信它校验了东西，你得先看它面对不存在的东西时会不会吭声。

五、复盘：这是我遇到的第四种「静默假绿」

写这个坑的时候我停下来数了数，这已经是同族的第四个了。

# 场景 绿色的东西 真实情况
1 Prometheus 采监控 up = 1，连续 35 小时 采到的是另一台机器的数据
2 Prometheus 采监控 up = 0，连续 27 小时 机器活得好好的，只是采集侧断网
3 grep 搜日志 退出码 0 一个都没搜到，因为关键词不对
4 本次：CHECKSUM TABLE 输出有行，退出码 0 一张表都没校验，因为表名不存在

第 3 个是 11-03 踩的。当时我总结成「grep 返回 0 是最危险的输出」——因为它区分不了「不存在」和「词不对」。

今天这个是同一族的升级版：grep 至少还会告诉你「没找到」，而 CHECKSUM TABLE 给你造了一个看起来完美的假结果，还配上了 NULL 这个在 SQL 里显得很专业的值。

⭐ 我给自己总结的通用判断方法，叫「阴性对照」：

任何校验/监控/断言类命令，在信任它之前，先用一个「必然失败」的输入去测它。
它面对失败会不会吭声，决定了它的绿灯能不能信。

这条在三个层次都成立：

  • 校验器层面 —— 传一个不存在的表名，看它报不报错（本次）
  • 被校验对象层面 —— 先 diff 表清单，确认「要校验的东西」本身是对的（本次）
  • 脚本层面 —— 明确把 NULL、空输出、非零退出码都判为失败，而不是「没报错就算过」

它回答的是「服务好不好、还有没有人在写」，而不是「两端数据一不一样」。这两件事，需要的是两类完全不同的工具。

六、今日收获

  1. 「校验通过」这句话，必须先证明校验器会失败才有意义。 一个面对不存在的对象只会回 NULL 的校验器，它给出的每一个绿灯都是空的。
  2. 迁移验收不能只有 checksum 一层。 表清单 diff → 行数/业务指纹 → 逐表 checksum，三层缺一不可：只有 checksum 会漏表（表不存在 → NULL → 假绿），只有行数会漏内容。
  3. NULL 不是「失败」，是「没东西可算」。 这两件事在脚本的字符串比较里长得一模一样——所以「把 NULL 显式判为失败」这一行代码，比你以为的值更重要。

顺便记一下今天的另一个收获，跟 MySQL 无关但同样重要：

迁移演练卡在了目标机的 root 登录上——ERROR 1045，而且 /var/log/mysqld.log 里 grep 不到 temporary password。

我一开始以为是密码记错了。查 /var/lib/mysql 才发现 auto.cnf、binlog.000001、ibdata1 全都在——这个实例是别人初始化的，口令根本没被记录下来。

这不是「密码错了」，这是「这个实例不属于我」。排障时先确认对象的来历，比反复重试密码有效得多。
