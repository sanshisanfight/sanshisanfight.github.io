【运维实战】看板四个数字加起来比总数还多，根因是两个统计桶重叠

发表于2026-11-11|更新于2026-11-11|云原生运维
|总字数:4.5k|阅读时长:17分钟|浏览量:

「已超期 3 + 本周待办 5 + 本月待办 8 + 今年待办 12 = 28」，
而看板最上面「全局总览」里的「待办 / 进行中」只有 21。

四个分桶加起来，比总数多 7。

第一反应当然是「数据错了」。但用户点开「超期工作」红色清单一看，那几条数据都真实存在、截止日期也没错、状态也确实是进行中。

这篇文章讲的就是这多出来的 7 是从哪冒出来的，以及怎么在 15 分钟内证明它。

一、先排除三个「看起来最像」的方向

排查这种「两个数字对不上」，最省时间的做法不是盯着数字看，而是按「从外到内」的顺序逐层证伪。我排了三个方向，每个都只花了几分钟。

方向 1：是不是界面渲染叠了？

用户报的现象是「全局总览和下面的卡片冲突」——「冲突」这个词第一反应是布局重叠。

翻样式文件：

全部是标准文档流：卡片有 margin-bottom，只有右下角悬浮按钮和弹层是 position: fixed。
没有任何 position: absolute 的卡片 → 视觉上不会真的叠在一起。

❌ 结论 1：不是布局问题。用户说的「冲突」是语义上的对不上，不是像素上的重叠。

方向 2：是不是两边查的数据范围不一样？

驾驶舱的「全局总览」和下面那四张统计卡，如果是两次数据库查询、两次不同的 where 条件，那就极可能是「统计卡的数没按你的权限过滤」。

读云函数，答案是恰恰相反——它们来自同一次查询：

同一批 all、同一个 now、同一套权限裁剪。
→ 两边看到的「数据集合」一模一样，连「已归档的任务被 continue 跳过」这一步都是共用的。

❌ 结论 2：不是数据范围打架。问题出在「同一批数据被切成了不同的桶」，而不是「切成了不同的数据」。

方向 3：桶的定义本身

既然是同一批数据、同一套范围，那差异只可能出在判定条件上。找到两个地方：

两个函数，同一套口径，两份实现。 这已经是个信号了——先记下，回头说。

⭐ 本质：这不是「时间区间算错了」，是「桶的定义压根不是区间」。
「已超期」是一个谓词（比 now 早），「本周待办」是一个时间段（本周一到本周日）。用一个谓词和一个时间段并排放，交集必然非空——因为 now 本身就落在本周内。

三、修复：让四个桶真正互斥

3.1 两种改法，选哪种？

方案 做法 问题
A. 删掉「已超期」桶 只留三个时间桶 超期工作会混进「本周/本月/今年」里，超期这个最需要被看到的状态被埋掉了；而且已有的「超期工作」红色清单会失真
B. 时间桶只统计未超期 ✅ week/month/year 三桶的下界改成 now 「已超期」与三个时间桶天然互斥；超期工作一个都不丢，继续由独立的「超期工作」清单承载

选 B。

3.2 完整改动

两处同源实现必须一起改——这是本次最容易翻车的地方：

为什么下界直接写 now，而不是写成 d >= weekStart(now) && d >= now？
因为 now 必然 ≥ weekStart（weekStart 是本周一 00:00），d >= now 已经隐含了 d >= weekStart。写成两个条件只是冗余，还让人误以为「周末的活儿会被漏掉」——不会，now 是流动的，周日 23:00 看到的「本周待办」就是周日剩下的那几小时。

这个「≤」是正确的；如果哪天有人把它改成「=」，反而说明又漏算了远期任务。

📌 顺手发现的一个小东西（不影响本次修复）：yearEnd 里的 setMonth(12) 会把月份推到次年 1 月，再 setDate(31) → 上界实际是次年 1 月 31 日，不是本年 12 月 31 日。
这不影响互斥性（四个桶仍然首尾相接构成一个划分），但「今年」这个桶其实多吃了下一个月。既然读到了就记一笔。

光跑通不算验证。得先证明这个脚本面对「必然会错的输入」会报错。

但这里冒出一个我一开始没想到的结论——请注意第二行：

「四桶合计 ≤ 未完成总数」这个断言，在 bug 存在的时候也 PASS（6 == 6）。
它区分不出对错。

为什么？因为在这组样本里，「被重复计数的 1 条」正好被「不落在任何桶里的 1 条」抵消了 —— 一个虚高、一个漏低，净效果为零。
真实环境里之所以会出现「28 > 21」，是因为重复计数的条数多于落在所有桶之外、却仍算在总数里的条数。

👉 这直接推翻了我一开始的判断。 我原本打算写「四桶合计 ≤ 待办/进行中」作为修复后的验收标准——那是一条假绿标准：它在 bug 存在时也通过。
真正能区分对错的，只有「没有任何样本同时命中两个桶」这一条。

⭐⭐ 这是本次最值钱的一条元教训：
一个只验证「结果看起来合理」的断言，等于没有断言。
「合计没超过总数」看起来很合理、很自然、甚至很像一条正确的验收标准 —— 但它对本次 bug 完全不敏感。
验收标准必须选那个「必然会失败的输入面前会失红」的那条。
这跟 11-09 那次「CHECKSUM TABLE 对不存在的表返回 NULL」是同一族：校验器没报错，不等于它校验了你想让它校验的东西。

五、复盘：这类「看板数字对不上」的通用排查法

5.1 「四个数加起来 > 总数」，只有三种成因

成因 特征 判别方法
① 桶重叠（本次） 某个样本同时落进两个桶 构造「边界样本」逐个探
② 口径不同 一边含已完成/已归档，另一边不含 把两边的过滤条件逐条对齐打印，看差在哪一条
③ 采样窗口不一致 一边是实时点查，一边是预聚合 比对两边的时间戳，不是比数字

排查顺序建议：② → ③ → ①。因为 ② 和 ③ 是「口径没对齐」，一眼能看出来；① 是「区间算错了」——它藏在两个看起来都很正确的条件里，是最贵的一种。

5.2 区间型统计的三条铁律

  1. 桶必须是「划分」而不是「筛选」。
    判定条件应该构成一个划分（partition）：每个元素恰好落进一个桶。
    一旦某个桶是「谓词」（比 X 早 / 比 Y 晚），它就必须显式排斥其他桶的区间，否则交集非空。

  2. 所有桶的参照物要统一。
    本次事故的深层原因是：「已超期」用 now 做参照，「本周待办」用「本周一」做参照。
    修复后四个桶全部以 now 为原点按区间切分 → 天然互斥。
    👉 同一组桶，参照物必须同源。

  3. 同源的两份实现，一起改。
    本次的 bucketWhere（数据库查询）和 inBucket（内存统计）是同一口径的两份代码。
    只改一处 → 列表页和看板口径分裂，比原来的 bug 更难解释（因为「总览对不上」变成了「两个页面对不上」）。
    👉 排查时一旦发现「同口径两份实现」，先把它记下来，修的时候一并动。

5.3 再加一条：验收标准本身也要被验收

「合计没超过总数」是一条看起来无比合理、实则完全无效的验收标准。
它符合直觉、读起来像一句正确的需求（「四个分桶应该不超过总数吧？」），但它对本次 bug 不敏感。

👉 写验收标准时，要问一句：「如果 bug 还在，这条断言会红吗？」
答不上来，就换一条断言。

六、今日收获

1. 「区间」和「谓词」混用，是分桶统计最贵的 bug。
「已超期」是谓词，「本周待办」是区间，两者在同一组里并排，交集必然非空。修法不是「把某个桶算准一点」，而是把整组桶的参照物统一。

2. 互斥性只能靠「必然冲突」的输入来证伪，不能靠读代码。
我构造的那条「本周内已过期」就是探针。它在修复前 FAIL、修复后 PASS，这才是验证器有意义的证据。一个永远绿的检查等于没有检查。

3. 验收标准本身也要被验收——尤其别用「看起来很合理」的那条。
我原本准备写「四桶合计 ≤ 待办/进行中」当验收标准，跑阴性对照才发现：它在 bug 存在时也 PASS。真正有效的只有「没有任何样本同时命中两个桶」。符合直觉的断言不一定是有效的断言。

（附带一条给做后台的同行）
看板上的数字是给人做决策的。决策者一旦发现两个数对不上，他就不会再相信这整个看板——他要么忽略它，要么忽略整个看板。所以「数字自洽」不是锦上添花，它是看板能不能被用的底线。
