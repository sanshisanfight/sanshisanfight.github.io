【运维实战】MySQL 报 1045 我查了 8 天：密码从来就不是原因

发表于2026-11-17|更新于2026-11-17|云原生运维
|总字数:4.1k|阅读时长:15分钟|浏览量:

一份待办清单，躺了 8 天

8 天前，我在自己的运维待办清单里记下了这么一条：

【阻塞】测试机 MySQL root 登录不了 —— ERROR 1045，日志里没有 temporary password，数据目录已初始化，疑似是别人装的实例。

“疑似别人装的实例” —— 这句话我当时觉得挺合理，甚至有点兴奋：这不就是典型的”接手了一个环境，密码在别人手里”的经典场景吗？

于是这条待办就一直在那儿挂着。每天看一眼，划掉，第二天再挂上。

直到昨晚，我在另一台机器上敲了一条几乎一样的命令，它报了个不一样的错：

1045 和 1698，两个都是”Access denied”，但它们根本不是一回事。

那一刻我意识到：我可能不是在查密码问题，我是在查一个错误的问题。

于是当晚我做了件事——把三台机器的登录方式挨个试了一遍，试出一张表。这张表告诉我，那 8 天里我追的方向，从第一步就是错的。

一、排查过程

1.1 先做最朴素的事：把报错原样抄下来

测试机 192.168.100.103（下面所有 IP 都是示例，下同）：

好，标准报错。教科书上说 1045 = 用户名或密码错误。改密码？重置？找初始化日志？

先别急。 这条报错里有一个被 99% 的人忽略的细节：

它的意思是”我这次是带着密码来的“。它没告诉你的是：服务端那个账号，到底有没有密码？

1.2 阴性对照：把”密码”这个变量摘掉再试

这是我最想推荐给大家的一个动作 —— 不要带着假设去试，要摘掉假设去试。

同一个账号，四种姿势各敲一遍：

结果：

# 命令 结果
1 不带密码 ✅ OK-no-pw
2 带错密码 ❌ ERROR 1045 ... (using password: YES)
3 空密码串 ✅ OK-empty-pw
4 查账号表 root | localhost | caching_sha2_password | （authentication_string 是空的）

它根本不需要密码。

我那 8 天里做的每一件事——找初始化日志、找 temporary password、怀疑是别人装的实例——都是在给一个空密码账号猜密码。

⭐ 这就是阴性对照的价值：不是”再试一次”，而是换一个维度去打掉原假设。原假设是”密码错”，那就去试”没有密码”这一个极端。极端能成立，中间那堆猜测就全没必要了。

1.3 换第二台机器：1698 是另一回事

同一时刻，主从复制的从库 192.168.100.102：

注意：没有 using password: YES/NO 这一段。而且这台机器我确实知道 root 是有密码的（主从环境里我自己设的）。

换个姿势：

auth_socket —— 这个插件的意思是：这个账号根本不看密码，它看的是”发起连接的 OS 用户是不是 root”。我用普通账号带密码连，它连密码都不读就直接拒了。

所以：

  • 1045：服务端读了你的密码，判定不匹配
  • 1698：服务端压根不读密码，只认 OS 身份

同一个 mysql -u root -p'xxx'，两种完全不同的拒绝理由。

1.4 再换第三台：2003 根本还没轮到认证

从主库 192.168.100.101 去连测试机的 3306：

113 = EHOSTUNREACH（主机不可达）。这是网络层的 errno，根本没走到 MySQL 的认证环节。

去测试机上看看：

ports: 是空的 —— 3306 没放行。

但等一下，为什么我在测试机本地用 mysql -u root 能连上，远程却不行？

因为本地走的是 unix socket，根本不经过网卡，firewalld 管不着它；远程走的是 ens160，一进防火墙就被 REJECT。

⭐ 同一个账号、同一个密码、同一个客户端，本地秒通远程超时 —— 这种”看起来矛盾”的现象，99% 是分层搞错了：不是认证问题，是网络层根本没到。

1.5 三台机器，三个错误码

机器 命令 报错 真实原因
192.168.100.101 主库 mysql -u root -p'xxx' ✅ 成功 root 是密码认证，密码正确
192.168.100.101 主库 sudo mysql（不带密码） ERROR 1045 ... (using password: NO) 有密码的账号，sudo 救不了它
192.168.100.102 从库 mysql -u root -p'xxx' ERROR 1698 auth_socket，不读密码
192.168.100.102 从库 sudo mysql ✅ 成功 OS 身份匹配
192.168.100.103 测试机 mysql -u root（不带密码） ✅ 成功 空密码账号
192.168.100.103 测试机 mysql -u root -p'xxx' ERROR 1045 (using password: YES) 多传了一个密码
192.168.100.103 测试机 远程连 192.168.100.103:3306 ERROR 2003 (113) firewalld 没放行 3306

同一句 mysql -u root -p'xxx'，在密码完全相同的前提下给出了三种错误码。

这一条事实，就足以证明：错误码不等于”密码错”。

二、根因：MySQL 到底拿什么做认证

2.1 账号的真相在 mysql.user 里

MySQL 判定”你是谁”，看的是这张表里的四元组：

字段 含义 举例
user 账号名 root
host 从哪个来源 IP/主机连过来 localhost / % / 192.168.100.%
plugin 认证插件 caching_sha2_password / auth_socket / mysql_native_password
authentication_string 密码哈希，空 = 空密码账号 $A$005$... / （空）

host 这一列是最容易漏的。 root@localhost 和 root@% 是两个完全不同的账号：

本地能登、远程登不上，很多时候不是插件问题，是你只有 root@localhost，压根没有 root@% —— 你拿 root@% 的密码去登 root@localhost，能成功才是见鬼了。

2.2 三种插件，三种行为

auth_socket（Debian/Ubuntu 默认给本机 root）

密码从头到尾没参与判断。传密码反而会触发这条路径的专属报错 1698。

caching_sha2_password（MySQL 8 默认）

关键就在”空”这一支：空密码账号，你传了密码它就拒，你什么都不传它就放行。

这解释了一个反直觉的现象 —— 报错信息里那句 using password: YES：

  • (using password: YES) = “我带了密码“ → 服务端说你带的这个跟库里对不上
  • (using password: NO) = “我没带密码“ → 服务端说这个账号需要密码

⭐ 这一行是 MySQL 报错里信息量最大的半句话。 它不告诉你密码对不对，它只告诉你你有没有带。而绝大多数教程只讲前半句，导致大家一看到 1045 就开始想密码。

mysql_native_password（老版本，8.0 里仍常见）
老式的 SHA1 认证，行为跟 caching_sha2_password 的”非空”分支一致。

2.3 mysql 不带 -u 会用 OS 账号 —— 这是第四种伪装

看起来是”连本机 MySQL”，实际上：

它用的是你的 SSH 账号名，不是 root。 报错长得跟”密码错”一模一样，但根因是你压根没说要以谁的身份登录。

这在脚本里尤其致命：脚本写成 mysql -e "..."，本机跑得好好的（OS 账号正好有权限），换个机器就全错。

三、解决方式

3.1 决策表：先看错误码，再看账号表

报错 层级 第一步查什么 解法
ERROR 1045 ... (using password: YES) 认证 SELECT user,host,plugin,authentication_string FROM mysql.user WHERE user='<你用的账号>'; 若 authentication_string 为空 → 不要传 -p；若非空 → 密码确实错了，或 host 不匹配
ERROR 1045 ... (using password: NO) 认证 同上 账号有密码但你没给 → 补密码；也可能是你忘了 -u（OS 账号顶上了）
ERROR 1698 (28000) 认证 plugin 是不是 auth_socket 是 → 改用 sudo mysql，或把插件改成 caching_sha2_password 并设密码
ERROR 2003 (HY000) ... (113) 网络 firewall-cmd --list-all / ss -lntp / ping 放行端口；确认监听地址；别在这层纠结密码
ERROR 2003 ... (2002) 网络 目标 IP 是否可达、MySQL 是否监听 同上

3.2 每个场景的具体命令（可直接复制）

场景 A：空密码账号 —— 别传 -p

场景 B：auth_socket —— 用 sudo，或改插件

改完记得确认 SSH 客户端是不是还在用旧的 auth 方式：

场景 C：远程连不上（2003/113）—— 放行端口 + 确认监听

场景 D：需要远程用 root 登录 —— 显式建账号

四、复盘与延伸

4.1 我这 8 天到底错在哪

不是”经验不够”，是方法错了。

我的原始假设是：“1045 = 密码错”。这个假设来自”报错这么写 + 教程这么讲”。然后我做的所有事情（找日志、找临时密码、怀疑是别人装的实例）全都是在这个假设的内部找证据，而不是去检验这个假设本身。

那个”打掉假设”的动作 —— 把密码摘掉再试一次 —— 只要 5 秒钟，却省了 8 天。

4.2 一条通用的排障方法：先分层，再定位

MySQL 连不上，正确的顺序永远是这三层，从上往下：

⭐ 错误码本身就带着分层信息：

  • 2003 = 你的 TCP 都没连上 —— 第 1 层
  • 1045 / 1698 = 连上了，是身份或凭据的问题 —— 第 2、3 层

很多人在第 1 层就输了，却跑去改第 3 层的密码。改密码当然没用，因为请求压根没到 MySQL。

4.3 一条更普适的原则：报错是症状，不是结论

这 8 天里我写下过一句很笃定的话：

“疑似是别人装的实例”

这句话我没有验证过，但因为它写在待办清单里、听起来合理，我就让它躺了 8 天。

而它最后被证伪的方式，朴素得让人有点想笑 —— 就是不带 -p 再敲一次。

⭐ 待办清单里的”根因”，在没有被证伪之前，它只是一个”当时的猜测”。 尤其当这个猜测已经躺了超过两天，它就该被降级回”待验证的假设”，而不是继续占用”已定位问题”的格子。

⭐ 一个坑的通用解法，比坑本身更值钱：我不知道下一个坑长什么样，但我知道怎么找它了 —— 给任何”报错 = 原因”的等式，做一次能证伪它的极端实验。

4.4 落地清单（可以直接抄）

  • 报错里先找 using password: YES/NO，再看错误码
  • sudo mysql -e "SELECT user,host,plugin,IFNULL(authentication_string,'<EMPTY>') FROM mysql.user;" —— 真相在这一行
  • 确认 host 列：root@localhost ≠ root@%
  • 脚本里所有 mysql 调用一律显式 -u <用户>
  • 本地能连远程不能 → ss -lntp + firewall-cmd --list-ports，别碰密码
  • 空密码账号 → 不要传 -p
  • auth_socket → sudo mysql，或改插件 + 设密码

五、今日收获

  1. 错误码是症状，不是结论。 同一句 mysql -u root -p'xxx'，在密码相同的前提下能给出 1045 / 1698 / 2003 三种错。先分层（网络 → 身份 → 认证），再谈原因。 报错里 using password: YES/NO 这一行告诉你的是”你有没有带密码”，不是”密码对不对”。

  2. 阴性对照是花 5 秒省 8 天的动作。 当你怀疑”是 A 导致的”时，构造一个”最极端的 A”去打掉它：怀疑密码错 → 试试完全不传密码。假设要被证伪，不能靠找更多支持它的证据。 这条对写脚本同样成立 —— 交付前先在”故意失败”的状态下跑一遍，看它会不会报红。

  3. 账号的真相在四元组里：user + host + plugin + authentication_string。 空密码账号、只认 OS 身份的账号、只允许本地连的账号，三种都长得像”密码错”，但解法完全不同。而 mysql 不带 -u 会悄悄用你的 OS 账号 —— 这一条最容易把人带进沟里。

折腾了一整晚，最后的结论是「密码从来都不是原因」。
所以那些查了八天的日志，其实一句都不用看。
